# `ndigo db` — Database-Adapter Abstraction (generic, multi-adapter)

**Status:** Draft plan (2026-11-06)
**Scope:** `@ndigo/orm`, `@ndigo/orm-drizzle` (and future `@ndigo/orm-*`),
`@ndigo/cli` db commands.
**Motivation:** The CLI's `db *` commands must stay engine-agnostic. Today they
front app-owned `db:*` scripts (already generic), but richer commands
(`push`, `pull`, `studio`, `seed`, `rollback`) risk hard-coding Drizzle
assumptions. Multiple databases per app also need unambiguous selection.

---

## 1. Adapter contract (`@ndigo/orm`)

Add a new module `packages/ndigo-orm/src/db-adapter.ts` exporting an
interface and supporting types. The CLI depends on **this interface only**,
never on a concrete ORM.

```ts
export type MigrationStatus = {
    version: number;
    description: string;
    applied: boolean;
    appliedAt?: Date;
};

export interface NdigoDatabaseAdapter {
    /** Stable, unique name used for selection (`--db <name>`). */
    readonly name: string;

    /** Human-readable engine label, e.g. "Drizzle (libSQL)". */
    readonly engine: string;

    /** Apply pending migrations. */
    migrate(): Promise<void>;

    /** Generate the next migration from entity metadata. */
    generate(): Promise<void>;

    /** Report applied/pending migration state. */
    status(): Promise<MigrationStatus[]>;

    /** Push schema directly to the database (dev convenience). */
    push?(): Promise<void>;

    /** Pull schema from the database into entity metadata. */
    pull?(): Promise<void>;

    /** Launch an interactive database browser (Drizzle Studio, etc.). */
    studio?(): Promise<void>;

    /** Run seed data. */
    seed?(): Promise<void>;

    /** Roll back the last (or N) applied migration. */
    rollback?(count?: number): Promise<void>;

    /** Close connections / release resources. */
    close?(): Promise<void>;
}
```

**Rules**

- Every method except `migrate`/`generate`/`status` is optional; the CLI
  advertises only what an adapter supports (`ndigo db --help` lists
  available actions per adapter).
- Adapters are **stateless factories**: the app constructs them with its
  own connection config (URL, credentials, schema path). The CLI never
  receives secrets.
- `@ndigo/orm-drizzle` ships `createDrizzleAdapter(options)` implementing
  the interface over `DrizzleMigrator` + the existing snapshot/generate
  pipeline. Future engines ship their own `@ndigo/orm-*` packages.

Export the new types from `packages/ndigo-orm/src/index.ts`.

## 2. Discovery & selection

### 2.1 Registry (preferred)

An app declares its databases in a conventional location:

```ts
// src/db.ts  (or src/database.ts, or a path in package.json#ndigo.databases)
import { createDrizzleAdapter } from '@ndigo/orm-drizzle';

export const databases = {
    primary: createDrizzleAdapter({ url: process.env.DB_URL!, migrationsDir: 'db/migrations' }),
    analytics: createDrizzleAdapter({ url: process.env.ANALYTICS_URL!, migrationsDir: 'db/analytics-migrations' }),
};

export const defaultDatabase = 'primary';
```

The CLI resolves the registry by trying, in order:

1. `ndigo.config.ts` / `ndigo.config.js` exporting `databases`.
2. A module path from `package.json` field `ndigo.databases` (string or
   `{ entry, default }`).
3. Conventional modules `src/db.ts`, `src/database.ts`, `src/db/index.ts`.
4. Auto-detect: if exactly one `@ndigo/orm-*` dependency is present and a
   default export exists at a conventional path, wrap it.

### 2.2 Selection rules

- `ndigo db <action> --db <name>` selects explicitly.
- If only one adapter is registered, it is used automatically.
- If multiple are registered and no `--db` is given:
  - TTY: prompt with the registered names (default marked).
  - non-TTY: fail with exit code 2 listing available names.
- `ndigo db list` prints registered adapters, engine labels, and the
  default.

### 2.3 Backwards compatibility

If no registry is found, the CLI falls back to the existing
`db:<action>` script convention (`db:migrate`, `db:generate`, `db:status`,
`db:new`). Apps that never adopt the adapter contract keep working
unchanged.

## 3. Runtime bridge

The CLI cannot import app code in-process (different module graph, no
workspace context). The app owns a tiny runner:

```ts
// src/db/cli.ts  (generated by `ndigo generate db-runner` or hand-written)
import { databases, defaultDatabase } from './db.js';
import { runDbCommand } from '@ndigo/orm'; // helper

export async function main(argv: string[]): Promise<number> {
    return runDbCommand(databases, defaultDatabase, argv);
}
```

`runDbCommand` (shipped in `@ndigo/orm`) parses `--db <name> <action>`,
resolves the adapter, invokes the method, prints a uniform summary, and
returns an exit code. The CLI invokes it through the existing one-shot
process lifecycle (`runAppOnce`-style spawn with signal relay) so
behaviour matches today's `db:*` scripts.

The CLI never calls ORM code directly; it only spawns the app's runner
with `--db <name> <action> [...args]`.

## 4. CLI updates (`@ndigo/cli`)

### 4.1 New / changed commands

| Command | Behaviour |
|---|---|
| `ndigo db list` | Print registered adapters + default. |
| `ndigo db migrate [--db name]` | Run `migrate()` (or fall back to `db:migrate` script). |
| `ndigo db generate [--db name]` | Run `generate()`. |
| `ndigo db status [--db name]` | Run `status()` and render a table. |
| `ndigo db push [--db name]` | Run `push()` if supported else exit 2 with "not supported by <engine>". |
| `ndigo db pull [--db name]` | Run `pull()`. |
| `ndigo db studio [--db name]` | Run `studio()` (long-lived; supervisor lifecycle). |
| `ndigo db seed [--db name]` | Run `seed()`. |
| `ndigo db rollback [--db name] [n]` | Run `rollback(n)`. |
| `ndigo db new [slug]` | Keep as-is (CLI-owned scaffold; engine-agnostic already). |

Global flag `--db <name>` added to every `db` subcommand (and to top-level
`ndigo db` route map docs).

### 4.2 Help / discovery

- `ndigo db --help` lists adapters when a registry is found (read via a
  lightweight `ndigo db --print-registry` probe that the app's runner
  supports, or by parsing the config file statically).
- Unsupported actions fail with exit code 2 and a clear message.

### 4.3 Generator support

- `ndigo generate db-runner` scaffolds `src/db/cli.ts` + a `db:cli`
  script, mirroring AD-85's app generator.
- `ndigo new` templates include an optional `--with-db <engine>` flag that
  wires the adapter + runner.

### 4.4 Implementation steps

1. Add `db-adapter.ts` + `runDbCommand` helper to `@ndigo/orm`; export
   types. Tests: adapter contract + `runDbCommand` selection logic.
2. Implement `createDrizzleAdapter` in `@ndigo/orm-drizzle` wrapping
   `DrizzleMigrator` and the existing generate pipeline.
3. Add discovery module to `@ndigo/cli` (config → conventional →
   auto-detect), with unit tests.
4. Update `@ndigo/cli` db commands to use discovery + `--db` flag, keeping
   script fallback.
5. Add `ndigo generate db-runner`.
6. Update app templates + `ndigo new --with-db`.
7. Docs: guide 25, ARCHITECTURE package map, README.

### 4.5 Exit codes / errors

- Unknown adapter name → exit 2, list available.
- Multiple adapters, no `--db`, non-TTY → exit 2.
- Unsupported action → exit 2.
- Adapter runtime failure → propagate child exit code (1).

## 5. Open questions

- Should `push`/`pull` be adapter-optional or always required? (Proposed:
  optional; CLI reports unsupported.)
- Should the runner be a script (`db:cli`) or a generated binary? (Proposed:
  script, consistent with existing `db:migrate`.)
- Where should the registry live by default — `src/db.ts` or
  `ndigo.config.ts`? (Proposed: both supported; `ndigo.config.ts` wins if
  present.)

# AD-19: Content/i18n — own the contract, wrap i18next, use `Intl` directly

**Date:** 2026-09-13
**Status:** Accepted — decision recorded; implementation sequenced (see
[plan](../plans/2026-09-13_CONTENT_I18N.md), not yet started)

## Background

`@ndigo/content` is a content-_resolution_ layer: `ContentSource` key lookup
with language fallback (static/composite/priority/TTL/negotiating sources),
themes, and an `Accept-Language` parser. The dispatcher carries a
`LanguageResolver` strategy (`NavigatorLanguageResolver('en-US')` default)
whose resolved language today feeds **view-name resolution only**
(`_resolveViewName(viewName, language)`) — it never reaches content lookup,
templates, or formatting. `ApplicationContext` implements `ContentSource`
and injects it into `ContentSourceAware` entries.

What is missing is the i18n half: message formatting (interpolation,
plurals, contexts), locale-aware date/number/relative/list formatting,
locale persistence and reactive switching on the client, lazy locale
loading, and SSR hydration-safety rules. The framework gap analysis
(`docs/audits/2026-09-13_FRAMEWORK_GAP_ANALYSIS.md` §4) identifies this as
the largest functional gap versus enterprise frameworks.

The question is how much ndigo implements versus delegates. ndigo has
already settled this exact question three times: `@ndigo/signals` re-exports
`@preact/signals-core`; validation deleted a home-grown system for **Zod**
(AD-07); telemetry wraps **OpenTelemetry**. The reference framework and ASP.NET own the
contract (`MessageSource`/`LocaleResolver`; `IStringLocalizer`) and delegate
engines to the platform standard (`ResourceBundle`/`MessageFormat`;
`CultureInfo`/`ResourceManager`). AdonisJS owns its i18n contract and
delegates to `@formatjs/intl` (ICU). The JS platform standard for
formatting is `Intl` (full ICU in Node ≥22 and all browsers, zero data
downloads); the de-facto standards for message translation are **i18next**
(largest ecosystem) and **ICU MessageFormat** via `@formatjs/intl`
(standards-aligned; `Intl.MessageFormat` is a TC39 Stage-3 proposal).

## Decision

### D1 — `MessageSource` contract in `@ndigo/content`, composing `ContentSource`

New interface in `@ndigo/content`:

```ts
interface MessageParams {
    /** Named interpolation values (`{name}` placeholders). */
    values?: Record<string, unknown>;
    /** Plural count (drives i18next `_one`/`_other` keys or ICU plural). */
    count?: number;
    /** Variant selector (i18next context suffix; ICU `select`). */
    context?: string;
}

interface MessageSource {
    /** Formatted message for `key`, falling back to `key` when missing. */
    getMessage(key: string, params?: MessageParams, language?: string): string;
}
```

`MessageSource` composes `ContentSource` (a message is a formatted content
key) so the theme/content-key hierarchy stays authoritative. It gets the
same treatment as `ContentSource`: `MessageSourceAware`/`AsMessageSourceAware`
mixins, `likeMessageSource` guard, and injection through
`ApplicationContextAwareProcessor`. `ApplicationContext` itself implements
`MessageSource` (delegating to the registered message-source entry,
falling back to raw `ContentSource` lookup) — the reference shape, making
`getMessage` available anywhere a context is.

### D2 — i18next is the reference implementation, in an adapter package

New package **`@ndigo/content-i18next`** (the `ndigo-orm` / `ndigo-orm-drizzle`
adapter precedent) implements `MessageSource` over an i18next instance:

- Resource storage, interpolation, plurals (via `Intl.PluralRules`
  underneath), contexts, fallback chains, and lazy loading are i18next's —
  ndigo never reimplements them.
- The adapter owns i18next instance lifecycle (`createInstance()`, no global
  singleton), language switching, and backend wiring (http-backend /
  dynamic import per locale).
- `@ndigo/content` stays dependency-free (core/factory/util only); i18next is
  a dependency of the adapter package, not the foundation.

The contract stays open: an ICU/`@formatjs/intl` backend (`FormatJSMessageSource`)
is a documented alternative implementation satisfying the same interface,
so a later ICU migration is a drop-in.

### D3 — Formatting uses `Intl` directly, behind thin ndigo wrappers

All date/number/relative/list/plural-category formatting uses `Intl.*`
(`Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`,
`Intl.ListFormat`, `Intl.PluralRules`) — never reimplemented. Four thin
wrappers (`DateTimeFormatter`, `NumberFormatter`, `RelativeTimeFormatter`,
`ListFormatter`) live in `@ndigo/core` next to `converter.ts`
(conversion-adjacent; `ConversionService` already lives there), each:

- caching one `Intl` instance per `(locale, options)` key — `Intl`
  constructors are expensive;
- taking **explicit `locale` and `timeZone` parameters**, never ambient
  server defaults — the SSR-hydration-safety rule (§D5).

### D4 — Locale resolution extends the existing `LanguageResolver` family

The dispatcher's `LanguageResolver` strategy (Navigator default today)
gains `FixedLanguageResolver` and `AcceptHeaderLanguageResolver`
(server; reuses the `Accept-Language` parsing already in
`@ndigo/content/src/negotiation.ts`). Client persistence and reactivity are
platform concerns:

- `@ndigo/platform-web`: cookie/localStorage-backed language resolver,
  persisted user override, and a **locale signal** (`@ndigo/signals`) so
  switching language re-renders views and re-formats without a reload.
- `@ndigo/platform-node`: `AcceptHeaderLanguageResolver` as the server
  default; resolved language exposed on the route/request so handlers and
  views can format and look up messages.

Precedence: explicit user choice > header/navigator > fixed default.

### D5 — SSR hydration parity is a first-class rule

A server-rendered date in server-local timezone will not match the client's
re-render, breaking island hydration. Rule: formatters take explicit
`locale` and `timeZone`; server rendering uses the request locale and a
pinned timezone; the resolved locale flows through the island contract
(AD-09) so server and client produce identical output.

### D6 — Non-goals (explicitly out of scope)

- **No formatting engines**: plural-rule tables, ICU parsing, CLDR data,
  resource formats — all delegated or engine-shipped.
- **No resource-format invention**: i18next JSON (or ICU) resource format
  only.
- **No message-broker / distributed i18n**, no translation-management
  tooling, no content-authoring UI.
- **No `@ModelAttribute`-style locale parameter injection in this change** —
  locale is exposed via the request/route and the `MessageSource` context;
  a `@locale` handler parameter is a later convenience, not a prerequisite.

## Consequences

- `@ndigo/content` gains the message contract without gaining a runtime
  dependency; i18next weight is isolated in `@ndigo/content-i18next`.
- `ApplicationContext` grows a `getMessage` path (delegating), mirroring
  The reference `ApplicationContext extends MessageSource`.
- One new package (`@ndigo/content-i18next`), one new `MessageSource` aware
  surface, four small formatter classes in `@ndigo/core`, two new language
  resolvers, and platform wiring. No existing behavior changes; all
  additions are additive.
- The gap analysis's "Content/i18n" entry moves from gap to
  implemented-by-plan when the phases land.
- The framework gains a client-side i18n story the reference framework does not have:
  reactive locale switching, persisted user preference, and hydration-safe
  server rendering.

## Implementation status (2026-09-13)

**All phases landed** (plan [`docs/plans/2026-09-13_CONTENT_I18N.md`](../plans/2026-09-13_CONTENT_I18N.md)):

1. `MessageSource` contract in `@ndigo/content` (`message-source.ts`).
2. `@ndigo/content-i18next` package with `I18nextMessageSource`.
3. `Intl` formatters + `FormattingService` in `@ndigo/core` (`formatter.ts`).
4. `ApplicationContext extends MessageSource` with context injection and
   hierarchical fallback.
5. Locale flow: `FixedLanguageResolver`/`AcceptHeaderLanguageResolver` in
   `@ndigo/dispatcher`; node adapter writes the header attribute and
   `NodeAutoConfiguration` negotiates via Accept-Language (e2e-verified);
   `@ndigo/platform-web` gained `CookieLanguageResolver`, the
   `currentLocale` signal + `changeLocale()`.
6. Templates + islands: `EJSLocaleHelpers` (`t`/formatters/locale) in every
   EJS render; `data-ndigo-locale` on island markers, assigned on hydration;
   route-attribute constants now live in `@ndigo/router`
   (`LANGUAGE_ATTRIBUTE`, `ACCEPT_LANGUAGE_ATTRIBUTE`) with dispatchers
   writing the negotiated language onto the route.
7. Demo gates: `ndigo-island` serves a fully localized SSR page negotiated
   from `Accept-Language` (translated strings, localized date, island
   locale attribute); `ndigo-todo` has a reactive locale switcher
   (cookie-persisted, signal-re-rendered, no reload).

Verification: build 30/30, tests 35/35 (incl. both demos), lint +
manifest + format clean, graft refreshed. Phase 4 (docs) landed: guide
`docs/guides/04-i18n-and-content.md`, plan moved to Completed, audit §4
marked implemented — all four phases done.

## Revisit Trigger

- **`Intl.MessageFormat` reaches Stage 4 / wide support** → evaluate an
  ICU-native backend as the default over i18next (drop-in behind the
  contract).
- **A consumer needs non-i18next resource loading** (custom store, CMS
  integration) → implement a second `MessageSource` backend against that
  store rather than extending i18next.
- **Server-rendered locales must be cached per request** (performance) →
  revisit per-request `MessageSource`/formatter scoping.

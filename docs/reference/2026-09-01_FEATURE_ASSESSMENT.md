Framework defects surfaced by the Wave-A work — **all resolved 2026-09-13**:

1. ~~`ApplicationBuilder.properties()` — the `'boot'` property source does not resolve~~ — **Fixed**: property sources normalize dotted keys (`server.port`) into nested objects at registration, so builder/env/file sources resolve through the context environment.
2. ~~`@configurationProperties` numeric `@defaultValue` conversion returns the raw string~~ — **Fixed**: the `@property` decorator no longer nulls fields, so the binder infers the declared initializer type and converts numerically.
3. ~~`@profile`-gated entry methods skipped~~ — **Fixed**: `ConfigurationParser` is created lazily per use, evaluating gates against the prepared environment (builder profiles).
4. ~~`ManagementAutoConfiguration.handlerMappings` shadows other app routes~~ — **Fixed**: a `handlerMappings` collection now _supplements_ the platform `handlerMapping` (appended as final fallback in the mapping strategy); ndigo-api boots the auto-config directly.
5. ~~relative `baseURL` / relative `Request` URL throws "Invalid URL"~~ — **Fixed**: the HTTP client only trusts absolute base URLs; the demo uses a same-origin absolute endpoint.
6. View-engine contract: components render via the `model` setter — **Documented** in `WebComponentView` TSDoc + the `ndigo-views` client demo.
7. **New (Wave B):** `CacheInterceptor`/`RetryOnOfflineInterceptor` `new Request(response.url)` on empty stub URLs → 418 — **Fixed**: unkeyable responses (`!response.url`) are skipped, not replayed/cached.
8. **New (Wave B):** Accept-header negotiation was never plumbed — the strategies read a `mediaTypeHint` nobody set, and `PathExtensionContentNegotiationStrategy` claimed a `super.resolveMediaTypes` it doesn't inherit — **Fixed**: the manager bridges `Accept` → hint from Node request headers (dispatcher), and the strategy falls back to the hint filter when no extension matches.

**Still open (demo slices, not defects):** telemetry-depth demo (request-id correlation across the chain, OTLP/span export — needs an exporter seam or collector; the correlation utility exists in `@ndigo/service`); CSRF/CORS interceptor wiring demo (lowest value).

## 3. Gaps & Decisions

### 3.1 Should Build (High Priority)

#### Signals (Rewrite `@ndigo/reactive` → `@ndigo/signals`)

Current `@ndigo/reactive` uses a **pull-based** observable pattern (Knockout-style `get()`/`subscribe()`). The industry standard has moved to **signals** — a **push-based** model with automatic dependency tracking.

**Drivers:** Signals are strictly better: no manual `.subscribe()`/`.unsubscribe()`, no memory leaks, automatic granular updates, better performance (no diffing), simpler mental model. Every major framework has adopted them (Solid, Preact, Angular 17+, Vue 3, Qwik).

**Plan:** `docs/plans/2026-09-01_SIGNALS.md`

#### Server-Rendered HTML Pipeline

Ndigo can render views on the server (it has the pieces — `ContentNegotiationViewResolver`, `@ndigo/platform-node`), but there's no clear SSR pipeline. The goal is not Next.js-style SSR/SSG (compile-time + Vite). The goal is **server-rendered + template-driven**: request → dispatcher → view resolver → template render → HTML response.

**Why:** Ndigo is a backend framework first. Sending HTML from the server is the primary interaction model. The current architecture supports this but the pipeline isn't wired end-to-end through `@ndigo/platform-node`.

**Not planned:** SSG / ISR / Streaming SSR — those are Vite/Next.js territory and conflict with Ndigo's runtime-first architecture.

#### Testing Harness (`@ndigo/test`)

No integration test support. Every package tests in isolation via Vitest. No equivalent of an in-process test harness or test context caching.

**Why:** Critical for adoption. Developers need to test their Ndigo applications, not just library internals.

| **Micro frontend shell**     | Already half-built (`FeatureContextMountManager`, context hierarchy, route partitions). Unique advantage — the reference framework has nothing equivalent. | Finish lazy loading, add shared dep management, typed contracts.                                                                                                                |
| **Type-safe routing**        | Modern JS expectation (tRPC, TanStack Router). Ndigo's routes are stringly-typed (`"users/{id}"`).                                                         | Template literal types + zod at route binding.                                                                                                                                  |

### 3.3 Won't Build (Intentionally Skipped)

| Reference feature                        | Why Skip                                                                                                                                                                                                                                                                   | JS Idiom                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **AOP with pointcuts**                   | Java needs AOP because it can't intercept methods without bytecode weaving. JS already has first-class interception: higher-order functions, decorators, Proxy, interceptor chains. A pointcut language (`execution(* service.*(..))`) would be an ugly Java import in JS. | Use TC39 decorators, interceptor chains, or a simple `withAround()` utility in `@ndigo/core`. |
| **SSG / ISR**                            | Compile-time rendering is a Vite/Next.js concern. Ndigo is a runtime framework.                                                                                                                                                                                            | Not planned.                                                                                  |
| **Messaging (JMS, RabbitMQ, Kafka)**     | Enterprise integration concerns. The reference framework's messaging abstractions are heavy. JS has excellent native libraries for each broker.                                                                                                                            | Use `amqplib`, `kafkajs`, `ioredis` directly.                                                 |
| **Distributed systems (Cloud, Gateway)** | Reference cloud tooling solves problems that are less relevant in JS (JVM classloading, EAR deployments). JS has simpler deployment models.                                                                                                                                | Not planned.                                                                                  |
| **Reactive Web (WebFlux)**               | Ndigo is request-response MVC. Reactive streams add complexity without clear benefit for most apps.                                                                                                                                                                        | Stick with async/await + Promise-based pipeline.                                              |
| **GraphQL**                              | Good library ecosystem. No framework integration needed.                                                                                                                                                                                                                   | Use `graphql-yoga` or `mercurius` directly.                                                   |
| **Java-style `@Scheduled` cron**         | `node-cron` or `bull` are better JS-native solutions.                                                                                                                                                                                                                      | Document integration pattern, don't build.                                                    |
| **`@Value` property injection**          | TypeScript already has `import.meta.env` and `process.env`. An annotation adds ceremony without value.                                                                                                                                                                     | `@ConfigurationProperties` exists — that's enough.                                            |

| Feature                           | Status                                                                                                                                                                                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Express/Koa adapter**           | Useful but not blocking. Nitro/Hono compatibility is more modern.                                                                                                                                                                                                  |
| **`@Cacheable`**                  | ✅ Superseded — landed 2026-09-17 as **`@cached`** in `@ndigo/cache`: the AOP premise was wrong (the framework's decorator-wrapper interception needs no pointcuts). Client memoization (`memoize`) landed with it. TTL + manual eviction; `@cacheEvict` deferred. |
| **YAML config**                   | `fromConfig()` supports JSON. YAML/TOML can be added as a reader plugin.                                                                                                                                                                                           |
| **CLI scaffold (`create-ndigo`)** | Post-1.0 polish. Generators exist for packages.                                                                                                                                                                                                                    |
| **OpenAPI generation**            | ✅ Landed 2026-09-28 as **`@ndigo/openapi`** (AD-35): spec from dispatch metadata + Swagger UI; typed-client generation stays post-1.0 (ecosystem generators).                                                                                                     |
| **Configuration profiles**        | Environment-based conditional entries (`@whenNode`) exist. A `@Profile`-style activation adds little.                                                                                                                                                              |

## 4. Conclusion

Ndigo's strongest features (IoC, dispatcher, auto-config, validation) are production-ready. The single biggest architectural investment should be **signals** — it modernizes the reactive layer, unblocks view optimization, and replaces a dated Knockout/Backbone API with the industry-standard pattern. Everything else is either a smaller package or intentionally skipped.

**Immediate priorities:**

1. Signals — rewrite `@ndigo/reactive` → `@ndigo/signals`
2. Server-rendered HTML pipeline
3. Testing harness

# ndigo-ui — implementation plan

**Status:** Delivered (Phases 0–4; intake `ui sync`/`ui port` remains future work)
**Decision:** [AD-95](../decisions/2026-11-08_AD95_NDIGO_UI.md) — owned design
system; supersedes AD-69 D-1/D-5 and AD-71.
**Scope:** `@ndigo/ui` (tokens + contract), `packages/ndigo-ui` (registry
items), `tools/ui-intake`, `ndigo ui` command family, `ndigo-site` catalogue.

---

## 1. What is being built

A curated design system for Ndigo applications, distributed as **copy-in
source** through a shadcn-compatible registry. Behaviour comes from Zag.js
machines; markup and styling are owned. Tokens are the contract between the
package, applications, and the marketing site.

The system has four layers:

| Layer | Registry type    | Content                                                                  |
| :---- | :--------------- | :----------------------------------------------------------------------- |
| L0    | `registry:theme` | `--nd-*` tokens — palette, semantic colours, type, space, radius, motion |
| L1    | `registry:theme` | Base layer: element defaults that consume the tokens                     |
| L2    | `registry:ui`    | `<nd-*>` custom elements — native-first, Zag for behaviour, FACE         |
| L3    | `registry:block` | Compositions: app shell, auth, settings, data table, empty/error states  |

L0–L2 items import nothing from Ndigo. Only L3 blocks may import
`@ndigo/view-webcomponent` for island wiring.

Native-first items (`button`) ship as token-driven CSS on the platform
element; `<nd-*>` custom elements are reserved for primitives that need a
behaviour machine or coordinated parts.

## 2. Distribution

One source, three channels:

1. **GitHub registry** — `npx shadcn add ndigo-dev/ndigo/<item>` works with no
   infrastructure. The root `registry.json` includes
   `packages/ndigo-ui/registry.json`.
2. **Namespace** — `@ndigo` → `https://ndigo.dev/r/{name}.json`, generated
   into `ndigo-site/public/r/` from the same registry.
3. **npm `@ndigo/ui`** — token CSS exports plus the typed token catalog. No
   render path, no React, no styling dependency.

## 3. Package layout

```
packages/ndigo-ui/
  registry.json                  # items, shadcn schema
  tokens/ndigo-tokens.css        # canonical token source
  theme/base.css                 # opt-in element defaults
  src/token-*.ts                 # TokenName / TokenGroup / TokenDefinition / catalog
  src/resolve-token.ts           # var(--nd-*) helper
  registry/base/                  # copy-in base element + Zag controller
  registry/ui/<component>/       # copy-in element, css, spec, README, meta.json
  registry/blocks/<block>/       # copy-in EJS partial + island wiring
  ports/<upstream>/              # provenance + port notes
```

`registry/` is deliberately separate from `lib/`: `lib/` is the TypeScript build
output for the token API, while the registry tree is copy-in source that the
shadcn-compatible registry serves and the CLI installs into an application.

## 4. The scale mechanism

Full parity is only affordable if adding a component is mechanical. Phase 1
therefore builds the four mechanisms before the component count grows:

1. **`createZagElement(machine, options)`** — lifecycle, connect/disconnect,
   prop spreading, cleanup. Each primitive becomes markup, CSS, and a machine
   binding rather than a bespoke integration.
2. **Conformance suite** — axe, keyboard, focus, RTL logical properties,
   reduced motion, DSD fallback, FACE, gzip budget. One harness, invoked per
   item.
3. **`ndigo ui new <name>`** — fronts a new
   `@ndigo/generators:ui-component` kind (`GENERATOR_KINDS` +
   `FLAG_KEYS_BY_KIND` entries, guide 25 row).
4. **Coverage matrix** — `ndigo ui sync` compares the upstream base list to
   the local registry and writes
   `docs/reference/NDIGO_UI_COVERAGE.md` with `ported | native-only |
   planned | not-applicable`.

The parity ladder from the upstream list (~66 base items):

- **~24 CSS/markup primitives** — alert, aspect ratio, badge, breadcrumb,
  button, card, field, input, item, kbd, label, separator, skeleton, spinner,
  table, textarea, typography.
- **~30 behaviour primitives** — accordion, avatar, carousel, checkbox,
  collapsible, combobox, context menu, date picker, dialog, drawer, hover
  card, menu, navigation menu, pagination, popover, progress, radio group,
  resizable, scroll area, select, slider, switch, tabs, toast, toggle group,
  tooltip.
- **~13 composites** — calendar, chart, code block, command, data table,
  input OTP, message scroller, questionnaire, sheet, sidebar, trace.

Parity means **no unexplained gaps** in the matrix, not identical file counts.

## 5. Intake pipeline

Upstream source is React + Tailwind + Radix. A mechanical sync is not
possible, so the pipeline is split by determinism.

**Tool (`tools/ui-intake`, fronted by `ndigo ui …`)**

Status: `init`, `add`, `list`, `view`, `validate`, and `mcp` are implemented;
`search`, `sync`, `port`, and `doctor` are pending.

- `init` — write `ndigo.ui.json` (aliases, paths, flavour, registries).
- `add | list | view` — resolve and install registry items (`search` pending).
- `mcp` — expose the registry to MCP clients for discovery, validation, and
  installation.
- `sync` — fetch upstream catalogues, hash payloads, diff against
  `ui.lock.json`, report `new | changed | removed`, exit non-zero in CI.
  Pending; the local half already exists as the lock-drift guard in
  `packages/ndigo-ui/test/ui-lock.spec.ts`.
- `port <item>` — fetch the upstream payload into `.ndigo-ui/intake/<item>/`
  with provenance; never install it. Pending.
- `validate` — schema, licence allowlist, provenance completeness, target
  safety.
- `doctor` — token drift, stale lockfile, missing licence records. Pending;
  the lock-drift guard is the first slice.

`ui.lock.json` per item: `source`, `item`, `ref`, `upstreamSha256`,
`license`, `origin` (`ndigo` or `ported`), `portedAt`, `portCommit`.

**Skill (`agent-local/skills/ndigo-ui-port/`)**

Translation contract and review checklist: React → custom element; Radix
state → Zag machine; Tailwind → scoped CSS with `--nd-*`; Framer Motion →
CSS/WAAPI; FACE for controls; DSD fallback; axe + keyboard + RTL + gzip.
Generated into `.opencode/` and `.omp/` by `pnpm agents:sync`.

**Drift job** — weekly CI compares hashes for `ports/*` and opens an issue
with the diff summary. Detection and reproducible re-port; no auto-merge.

**Licence policy** — shadcn (MIT) and Cult UI (MIT) are intake-eligible with
provenance. Skiper premium items are inspiration only. Every other source
needs a recorded licence check before intake.

## 7. Testing

- Unit: token catalog ↔ CSS parity, `resolveToken`, registry item shape.
- Conformance: axe, keyboard, focus, RTL, reduced motion, FACE, DSD.
- Browser: Playwright in `apps/20-ndigo-ui-lab` for hydration and form
  submission through the existing `dataBinderValue` + Zod path.
- Budget: per-item gzip delta recorded in the item's `meta.json`.
- Docs: `pnpm doc:check` must be clean; `pnpm manifest:check` covers the
  README standard and dependency closure.

## 8. Risks

| Risk                                | Mitigation                                                                            |
| :---------------------------------- | :------------------------------------------------------------------------------------ |
| `@zag-js/vanilla` maturity          | Phase 1 spike gates the decision; fallback to `@zag-js/core` + `dom-query`            |
| Scope creep toward full parity      | Coverage matrix + the D-1 milestone ladder; shrink the promise, not the quality       |
| Accessibility debt                  | Conformance harness before components, not after                                      |
| Two visual languages (site vs apps) | Tokens move to the package in Phase 0; the site consumes them through its sync script |
| Port treadmill                      | Upstream is a reference after first port; drift queued, never merged                  |
| Single-lane files                   | Phase 0 touches `pnpm-lock.yaml`, `packages/ndigo-ui/api/`, `API.md`                  |

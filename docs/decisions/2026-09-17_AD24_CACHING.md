# AD-24: Caching — isomorphic store, `@cached` decorator, `memoize`

> **Current-contract supersession (2026-10-01):** The original decisions below
> remain historical. [AD-40](2026-10-01_AD40_PERSISTENCE_BASELINE.md), following
> [AD-39](2026-09-30_AD39_ASYNC_BY_DEFAULT.md), supersedes the synchronous
> Cache API and promise-return semantics via the async cutover: `get`/`set`/
> `has`/`delete`/`clear` and `size()` return promises; manager `getCache`/
> `hasCache` remain synchronous local handle-registry operations. `@cached`
> requires Promise-returning methods, and `memoize` always returns a promise
> even for synchronous input. Single-flight now spans backend read through
> computation and write, scoped to the actual store. Read errors reject;
> decorator write failures warn best-effort while returning the computed value.
> No distributed backend is introduced by this cutover. Current examples are
> in the [live caching guide](../guides/07-caching.md).

**Date:** 2026-09-17
**Status:** Accepted — decision recorded; implementation sequenced (see
[plan](../plans/2026-09-17_CACHING.md))

## Background

Server-side caching is gap-analysis item #4
(`docs/audits/2026-09-13_FRAMEWORK_GAP_ANALYSIS.md` §2.1): the framework had
only **client-side HTTP caching** (`CacheInterceptor` — in-memory TTL store
for GET/HEAD, LRU-ish by `lastAccessed`; `IfModifiedInterceptor` —
ETag/Last-Modified conditionals), plus two isolated TTL/eviction patterns
(`TtlContentSource`, `@blue/core`'s private `_lru-cache.ts`). No cache-aside,
no TTL store as a reusable abstraction, and no memoization anywhere.

The trigger question set the shape: Spring's answer is `@Cacheable` +
`CacheManager` + SpEL keys over AOP proxies. BlueJS's constraints (this
wave's owner decisions): **client-side memoization is in scope** (the audit
item reads server-side only, but the missing half is the same store), **no
AOP / no pointcuts / no expression language** (the repo's stated JS-idiom
position, assessment §3.3), and **no new `-able` decorator names** (verified:
zero `@[A-Za-z]+(able|ible)` decorators exist in any package — `@Cacheable`
would have been the first).

## Decision

### D1 — `@cached`, and the past-tense convention is the anchor

Named `@cached`, not `@cache` or `@cacheable`: it joins the repo's existing
past-participle/adjectival behavior-decorator family (`@scheduled`,
`@authenticated`, `@authorized`, `@generated`, `@transactional` — AD-20 D8),
pairing exactly with `@scheduled` (verb root + `-ed`, method execution
semantics). `-able` is the Spring echo the repo has never used, and a bare
noun (`@cache`) would be the first noun among behavior decorators —
stereotypes take nouns here (`@service`, `@entry`), behaviors take
participial/adjectival forms. The AD-20 D8 consistency review (1.0 freeze)
governs the whole family together; a rename of `@cached` is trivial pre-1.0.

### D2 — One isomorphic package `@blue/cache`; zero runtime dependencies

`Cache`/`CacheMiss`/`MemoryCache` (the store), `CacheManager`/`MemoryCacheManager`
(the named-cache registry), `memoize` (plain-function client memoization),
and `cached` (method decorator) share one package with **no runtime
dependencies** — isomorphic by construction, safe in browsers and Node, and
the home for caching going forward. `lru`/`fifo` eviction + TTL are store
options; the audit's "in-memory store" is the v1 boundary and
`Cache`/`CacheManager` are the extension seams for a distributed adapter.

### D3 — No AOP: decorator-returned wrapper with graceful degradation

The interception mechanism is the repo's own (`@transactional` precedent,
`blue-orm/src/decorators.ts:336-370`): `@cached` returns a wrapper function
that resolves the `CacheManager` off the instance (`this.cacheManager`,
constructor- or aware-injected) and **calls the raw method when absent**
(unit-test posture). No proxies, no pointcuts, no bytecode. Because the
wrapper replaces the prototype method, `this.method()` self-invocation is
cached — stronger than Spring proxy semantics (which bypass on
self-invocation); documented.

### D4 — Fulfilled results only; async single-flight is `memoize`'s job

Cache **hits** return the stored settled value; **misses** call the target
and store only fulfilled results — rejections/throws propagate and the next
call retries (a deliberate divergence from HTTP caching, which may store
error responses). Promise-aware writes mean async methods return the live
promise while the settled value is stored. Single-flight coalescing lives in
`memoize` (concurrent calls share one in-flight promise, then cache the
settled value); the decorator defers it (an async wrapper adds nothing until
a consumer exists).

### D5 — Keys are plain JS functions, not SpEL

`key: string` (one cached value) or `key: (...args) => string`; default is
JSON-serialized arguments (undefined/null collapse, insertion order
significant). No expression language, no argument binding — the framework's
stated position. Documented: args-only keys mean a shared manager collides on
equal args across instances; per-cache-name or per-instance managers are the
mitigations.

### D6 — Eviction: Map-order LRU default, `fifo` option; core's `_lru-cache` stays private

`MemoryCache` uses the O(1) Map-order LRU technique
(`@blue/core/src/_lru-cache.ts`: get-hit delete+reinsert, full → evict first
key) — strictly better than `CacheInterceptor`'s `lastAccessed` min-scan.
`eviction: 'lru' | 'fifo'` (default `lru`; FIFO = oldest insertion, no
promotion); `maxSize` omitted = TTL-only, no size eviction (the
`TtlContentSource` model). LFU/random are non-goals. The private core copy
**stays** for `URLGlobPathMatcher` — moving it would invert the dependency
direction (core is the base layer); `CacheInterceptor` is untouched (HTTP
cache semantics don't fit the generic store; unification is a post-1.0
option).

### D7 — Server wiring is the AD-20 zero-config pattern

`NodeAutoConfiguration` provisions a `cacheManager` `@entry` bean
(`MemoryCacheManager`); a registered class implements the `ApplicationContextAware`
mixin (the blessed `[$aware]` brand) to resolve it — exactly how
`ScheduleRegistry` receives the context. Browser apps need no wiring at all:
`memoize` is DI-free, and `@cached` works whenever the instance carries a
manager.

### D8 — Non-goals

No `@cacheEvict` in v1 (invalidation = TTL + `cache.delete/clear`); no
distributed/Redis store; no `CacheInterceptor` refactor; no second decorator
for store-scoped eviction. All are post-1.0 candidates behind the existing
interfaces.

## Consequences

- New dependency-free package `@blue/cache`; a `cacheManager` entry on
  `NodeAutoConfiguration`; `@cached` + `memoize` surface.
- Zero-config server adoption (bean present for every Node app), zero-config
  client adoption (`memoize`).
- Demo gates: `apps/blue-api` `GET /api/cached-report` (two dispatches, one
  computation — counter asserted in the bootstrap spec) and the `blue-views`
  client demo (memoized payload derivation beside the existing cache-hit
  refresh).
- The manual-invalidation contract is documented: `cacheManager`
  `.getCache(name).delete/clear` — the `@cacheEvict` ergonomic remains a
  revisit trigger.

## Revisit Trigger

- **`@cacheEvict`-style invalidation demand** (write-through/write-behind
  patterns in demos) → a second decorator + wrapper composition on the same
  metadata seam.
- **Distributed caching is required** (multi-process TTL store) → implement
  `Cache`/`CacheManager` against Redis (or a facade); call sites unchanged.
- **`CacheInterceptor` semantic overlap measured** (the HTTP cache's
  response semantics vs. the generic store) → unify behind `Cache` post-1.0.
- **1.0 API freeze** → the AD-20 D8 participle naming review decides the
  `@cached`/`@scheduled`/`@authenticated`/`@authorized`/`@generated`/
  `@transactional` family together, once, before release.

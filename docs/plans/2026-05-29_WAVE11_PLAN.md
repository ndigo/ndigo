# Wave 11 Plan: Benchmark Coverage, Hot-Path Optimization & API Hardening

**Created:** 2026-05-29
**Status:** Planned
**Depends on:** Wave 10 (committed)

---

## Overview

Wave 11 has three focus areas determined during the post-Wave-10 benchmark review session:

1. **Benchmark accuracy & coverage** — fix stale labels, fix a structurally weak bench file, and add missing coverage for the router, application context, and ORM.
2. **Hot-path Ramda replacement in `@blue/util/src`** — three source files use Ramda for logic that is called frequently from other packages; replace with native equivalents using the same pattern as `like.ts` (WeakMap-cached where appropriate, plain native otherwise).
3. **API hardening** — promote two `@experimental` APIs (`UnitOfWork` / `@transactional`) to stable by wiring up a `TransactionManager`, and re-evaluate `@blue/orm-drizzle` now that `pnpm add` is unblocked.

## Phase B: Hot-Path Ramda Replacement in `@blue/util/src`

These three files use Ramda for logic — not just as pass-through re-exports. They are called from other packages on the request path and are candidates for native replacement using the same approach as `like.ts`.

### B1 — `trailing-split.ts`

**Current:** Uses `trim`, `split`, `slice` from Ramda.
**Called by:** `@blue/parser` `from-piped-string.ts` — used on every URL/query-string parse.
**Replacement:** Direct native string methods (`str.trim()`, `str.split(sep)`, `str.slice(0, n)`).
**Risk:** Low — semantics identical; tests in `trailing-split.spec.ts` cover all edge cases.

```ts
// Before
import { slice, split, trim } from 'ramda';
// ...
t = trim(t);
return split(separator, isSeparatorTrailing && !isEmptyString ? slice(0, tail, t) : t);

// After (native)
t = t.trim();
return (isSeparatorTrailing && !isEmptyString ? t.slice(0, tail) : t).split(separator);
```

**File:** `packages/blue-util/src/string/trailing-split.ts`

### B2 — `to-string.ts`

**Current:** Uses `cond`, `T`, `always`, `identity`, `isNil` from Ramda for a 3-branch dispatch.
**Called by:** `@blue/validate` (`standard-constraints.ts`, `type.ts`) on every validation call.
**Replacement:** Plain native `if/else` — the three branches map trivially:

```ts
// Before
const toString = cond<any, string>([
    [isNil, always('')],
    [isString, identity],
    [T, _toString],
]);

// After (native)
function toString(value: any): string {
    if (value == null) return '';
    if (typeof value === 'string') return value;
    return _toString(value); // keep Ramda's toString for non-string serialization
}
```

**File:** `packages/blue-util/src/string/to-string.ts`

### B3 — `like-array.ts`

**Current:** Uses 13 Ramda imports (`cond`, `both`, `either`, `propSatisfies`, `gt`, `has`, `isNil`, `length`, `pipe`, `dec`, `toString`, `T`, `F`) for what is a 7-branch structural check.
**Called by:** `@blue/core` `collection.ts` — constructor argument type-guard.
**Replacement:** Native `if/else` chain replicating the exact branch logic:

```ts
// After (native) — all 7 branches preserved
function likeArray(value: any): value is ArrayLike<any> {
    if (value == null) return false;
    if (Array.isArray(value) || typeof value === 'string') return true;
    if (typeof value !== 'object') return false;
    const len = value.length;
    if (typeof len !== 'number') return false;
    if (value.nodeType === 1) return len > 0;
    if (len === 0) return true;
    if (len > 0) return '0' in value && String(len - 1) in value;
    return false;
}
```

**Risk:** Medium — semantically equivalent but removes Ramda entirely from this file. Covered by `like-array.spec.ts`.

**File:** `packages/blue-util/src/type/like-array.ts`

## Phase C: API Hardening (Deferred from Wave 10)

### C1 — Wire `TransactionManager` and promote `@transactional` to stable

**Current state:** `@transactional()` stores metadata via `Symbol.metadata` but no `TransactionManager` enforces transaction boundaries. Marked `@experimental`.

**Work required:**

- Define `TransactionManager` interface in `@blue/orm`.
- Implement `InMemoryTransactionManager` (wraps operations in a try/commit/rollback cycle).
- Integrate with `EntityManager` — `save()`, `remove()` check for an active transaction context.
- Update `@transactional()` to look up `TransactionManager` from the application context and wrap the decorated method.
- Promote `@transactional` and `UnitOfWork` from `@experimental` to `@since 1.0.0` in TSDoc.

### C2 — Re-evaluate `@blue/orm-drizzle`

**Current state:** Deferred in Wave 9/10 because `pnpm add drizzle-orm better-sqlite3` was blocked by the bash policy. That restriction no longer applies.

**Work required:**

- Create `packages/blue-orm-drizzle/` as a new package.
- Implement a `DrizzleEntityManager` that wraps a Drizzle `db` instance.
- Export `drizzleAutoConfiguration` for easy wiring via `@configuration`.
- Add integration tests using an in-memory SQLite DB (via `better-sqlite3`).

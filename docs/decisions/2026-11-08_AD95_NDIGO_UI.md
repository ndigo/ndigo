# AD-95: ndigo-ui — an owned design system, distributed as a code registry

**Date:** 2026-11-08
**Status:** Accepted — supersedes AD-69 D-1 and D-5, and AD-71 in full.
AD-69 D-2 (vetting checklist), D-3 (DSD/FACE bridge), and D-6 (no dependency
by default) remain in force, restated below in their new form.

## Context

AD-69 decided that Ndigo would not build a component library: the framework
would own the integration contract, components would come from the Web
Component ecosystem, and AD-71 selected Web Awesome as the single reference
integration. Both records were correct for the information available at the
time, and both assumed a colourless framework that ships no visual surface.

Three things changed:

1. **The distribution model changed.** shadcn's registry is now explicitly
   framework-agnostic. A GitHub repository with a root `registry.json` is a
   registry; `registry:item` distributes arbitrary files; namespaces let a
   project consume `@ndigo/button` from a URL template. The copy-in model no
   longer implies React.
2. **The behaviour half became framework-agnostic.** `@zag-js/vanilla`
   (1.47.0, MIT, published 2026-10-26) wraps 57 headless behaviour machines
   — the same machines behind Ark UI — with no framework runtime. Native
   elements plus Zag cover shadcn's behaviour surface without owning a11y
   state machines by hand.
3. **The design surface has no canonical home.** The brand palette, semantic
   colours, and typography exist only in the `ndigo-site` repository
   (`src/styles/tokens.css`). Every Ndigo application either invents its own
   design language or copies that file. AD-71's reference app demonstrates
   the bridge but not a look, a token contract, or a composition vocabulary.

The cost of leaving AD-69 in place is now higher than the cost of ownership:
no shared design language, no accessible reference implementation, and no
way for an adopter to go from "empty app" to "coherent UI" without making
every decision themselves.

## Decision

**D-1 — Own a curated design system, not a general kit.** ndigo-ui ships a
deliberate set: roughly 24 primitives and 10 blocks in the first milestone.
Full parity with shadcn's base component list is a milestone sequence, not an
architecture — the component contract, generator, and conformance suite are
designed so each additional component is mechanical. Anything outside the
set is composed from tokens, not absorbed into the package.

**D-2 — Behaviour comes from Zag.js; markup and styling are ours.** Native
elements first (`<dialog>`, the popover API, `<details>`, `:has()`), then a
Zag machine where the platform cannot supply the behaviour, wired through
`@zag-js/vanilla` inside a custom element. Pin the 1.x line; the 2.0-next
adapter contract is out of scope until it stabilises. No styled component
library is a dependency of the framework or of ndigo-ui.

**D-3 — Distribution is a registry, not a runtime package.** ndigo-ui items
are copy-in source described by a shadcn-compatible `registry.json`. The
`@ndigo/ui` npm package carries the token CSS, the typed token catalog, and
nothing with a render path. Consumers own the code they install; the package
never becomes a component runtime.

**D-4 — Tokens and elements are the public contract.** `<nd-*>` elements and
`--nd-*` custom properties. L0–L2 items (tokens, theme, primitives) import
nothing from Ndigo, so they install into Astro, EJS, or any HTML surface.
Only L3 blocks may import `@ndigo/view-webcomponent` for island wiring.

**D-5 — Consumer dependencies point one way.** ndigo-ui knows no consumer.
Starlight/Astro adapters live in `ndigo-site`; EJS and island blocks are the
Ndigo-application flavour. A reusable framework integration may later become
an opt-in registry item under `integrations/`, never a core dependency.

**D-6 — Conformance precedes components.** An item ships only after it passes
the shared suite: axe-clean, keyboard contract, focus management, logical
properties for RTL, `prefers-reduced-motion`, declarative-shadow first paint,
FACE participation for form controls, and a recorded gzip budget.

**D-7 — Intake is deterministic tooling plus an agent skill.** The tool
fetches, hashes, licence-checks, records provenance, and reports drift. The
skill encodes the translation contract (React → custom element, Radix state
→ Zag machine, Tailwind → `--nd-*` CSS, motion → CSS/WAAPI). Upstream is a
design reference after the first port; drift is detected and queued, never
merged automatically.

**D-8 — Licence policy.** Permissive sources (MIT and equivalent) may be
ported with recorded provenance. Premium or non-OSI sources are inspiration
only; no code is copied.

### Retained from AD-69

- **D-2 vetting checklist** becomes ndigo-ui's component acceptance
  checklist: licence, DSD/SSR, FACE, accessibility, theming, i18n, packaging,
  maintenance, bundle budget, and usable-without-wrappers.
- **D-3 bridge** becomes a requirement on every primitive: DSD first paint
  via the server-fallback pattern, and `AsFormAssociated(Base)` participation
  for controls, so the existing binding + Zod path is unchanged.
- **D-6 no dependency by default** becomes exactly one approved behaviour
  dependency (Zag.js) and no styling or component-library dependency.

## Rationale

- The registry protocol is the only distribution model that fits a framework
  that ships no components, and it is now framework-neutral.
- Zag gives shadcn's behaviour half without React. Porting className strings
  would produce unmaintainable CSS; porting anatomy and behaviour is the
  only durable translation.
- Theming a styled library cannot deliver shadcn's anatomy without
  wrappers, which AD-69 D-4 forbade. Ownership resolves the contradiction
  instead of hiding it.
- Tokens are the actual differentiator, and the brand already exists with no
  canonical source. Putting them in a package makes the site and every app
  consume the same values.
- A registry keeps the published surface honest: consumers can read every
  line before it lands in their project.

## Consequences

- Accessibility, i18n, RTL, form participation, SSR parity, and semver for
  owned components become first-party obligations. The conformance suite and
  the scope ladder are the controls, not optimism.
- `apps/07-ndigo-island` keeps its Web Awesome integration until Phase 3,
  then migrates to `<nd-*>` and the dependency is removed from the workspace.
- Guide 21 is rewritten from "select a library" to "use ndigo-ui"; the
  Web Awesome material survives as a historical appendix until Phase 3.
- `ndigo-site` imports the token CSS from `@ndigo/ui` and keeps its own
  Starlight mapping. The site never becomes a dependency of the package.
- Phase 1 gates on a `@zag-js/vanilla` spike (dialog + menu). If the adapter
  is insufficient, the fallback is `@zag-js/core` plus `@zag-js/dom-query`
  directly; both are the same machines.
- Adding a component now has a fixed cost: conformance, docs, registry
  entry, and a measured budget. That cost is the point.

## Revisit triggers

- `@zag-js/vanilla` proves unsuitable, or Zag 2.0 changes the adapter
  contract in a way the wrapper cannot absorb.
- The full-parity milestone stalls for two consecutive releases — shrink the
  promised set rather than letting the matrix rot.
- A maintained, framework-agnostic Web Component library emerges that passes
  the AD-69 D-2 checklist and removes the maintenance burden — re-evaluate
  D-2, not D-1.
- The upstream registry schema makes a breaking change that copy-in cannot
  absorb without a migration.

# Content/i18n — MessageSource, i18next adapter, Intl formatters, locale flow

**Date:** 2026-09-13
**Status:** Completed — all phases landed (2026-09-13)
**Packages:** `@blue/content` (contract), `@blue/content-i18next` (new adapter),
`@blue/core` (formatters), `@blue/dispatcher` (language resolvers),
`@blue/platform-node`, `@blue/platform-web`, `@blue/context` (context
integration), `apps/blue-island` + `apps/blue-todo` (demo gates)
**Depends on:** AD-19 (decision), `@blue/signals` (locale reactivity),
existing `@blue/content` sources and dispatcher `LanguageResolver` strategy

---

## 1. Motivation

`@blue/content` resolves content keys by language but cannot format
messages (interpolation, plurals, contexts), format dates/numbers/lists, or
react to locale changes on the client. The dispatcher resolves a language
string per route (Navigator default) but it only feeds view-name lookup —
it never reaches content, templates, or formatters. Enterprise frameworks
(Spring, ASP.NET, AdonisJS) own the contract and delegate engines to the
platform standard; this plan applies the same shape to BlueJS, per AD-19:

- **BlueJS owns:** `MessageSource` contract, locale resolver family,
  reactive locale state, thin `Intl` formatter wrappers, the wiring.
- **i18next implements:** message resources, interpolation, plurals,
  contexts, fallbacks, lazy loading — behind the contract.
- **`Intl` used directly:** all date/number/relative/list formatting.

## 2. Design

### 2.1 `@blue/content` — MessageSource contract

New `src/message-source.ts`:

```ts
import { ContentSource } from './content';

/** Interpolation values, plural count, and variant selector. */
export interface MessageParams {
    values?: Record<string, unknown>;
    count?: number;
    context?: string;
}

/**
 * Formats a message for `key` in the given language. Composes a
 * `ContentSource`: missing messages fall back to the key itself, matching
 * the content layer's fallback convention.
 */
export interface MessageSource {
    getMessage(key: string, params?: MessageParams, language?: string): string;
}
```

Follows the existing `ContentSource` surface pattern exactly:

- `AsMessageSourceAware` / `MessageSourceAware` mixin (mirrors
  `AsContentSourceAware` in `content.ts`).
- `likeMessageSource` duck-type guard (`like({ getMessage: Function })`).
- `CompositeMessageSource` / `PriorityMessageSource` over
  `MessageSource` if the composition sources prove useful (mirrors
  `composite.ts` / `priority.ts`); defer until a consumer exists.
- Re-export from `index.ts`.

`src/negotiation.ts` already exposes `parseAcceptLanguage` — reused by the
node language resolver (§2.4).

### 2.2 `@blue/content-i18next` — new adapter package

New package (the `blue-orm`/`blue-orm-drizzle` adapter precedent) depending
on `@blue/content` + `i18next`:

```ts
import { createInstance, type i18n, type Resource } from 'i18next';
import { MessageSource, MessageParams } from '@blue/content';

export interface I18nextMessageSourceOptions {
    resources?: Resource;                    // static resources (tests, SSR)
    language?: string;                       // default language
    fallbackLanguage?: string | string[];    // fallback chain
    /** Lazy-loading backend (e.g. i18next-http-backend). */
    backend?: object;
    /** Namespaces to load lazily. */
    ns?: string[];
    defaultNS?: string;
}

export class I18nextMessageSource implements MessageSource {
    readonly instance: i18n;                 // createInstance() — no global singleton
    constructor(options: I18nextMessageSourceOptions) { … }
    getMessage(key: string, params?: MessageParams, language?: string): string;
    /** Switch the active language (awaits loaded resources). */
    async changeLanguage(language: string): Promise<void>;
    /** Preload resources for the given languages. */
    async preload(languages: string[]): Promise<void>;
}
```

Mapping: `params.values` → i18next `replace`; `params.count` → i18next
`count` (plurals via `_one`/`_other` keys); `params.context` → i18next
`context` (`key_male`-style suffixes); missing keys return the key (i18next
`returnNull`/`returnEmptyString` off, consistent with the content fallback
convention). `language` argument overrides the active language per call.

### 2.3 `@blue/core` — Intl formatter wrappers

New `src/formatter.ts` (next to `converter.ts`; conversion-adjacent):

```ts
export interface FormatOptions { locale: string; timeZone?: string; }

export class DateTimeFormatter {
    constructor(options: { locale: string; timeZone?: string; dateStyle?: Intl.DateTimeFormatOptions['dateStyle']; timeStyle?: … }) {}
    /** Format a Date or ISO string; throws on invalid input. */
    format(value: Date | string | number, options?: Partial<FormatOptions>): string;
}

export class NumberFormatter { … }            // Intl.NumberFormat
export class RelativeTimeFormatter { … }      // Intl.RelativeTimeFormat
export class ListFormatter { … }              // Intl.ListFormat

/** Cached per-(locale, options) Intl instances; registry-style factory. */
export function createFormattingService(options?: FormattingServiceOptions): FormattingService;
export interface FormattingService {
    date(options?: DateTimeFormatterOptions): DateTimeFormatter;
    number(options?: NumberFormatterOptions): NumberFormatter;
    relativeTime(options?: RelativeTimeFormatterOptions): RelativeTimeFormatter;
    list(options?: ListFormatterOptions): ListFormatter;
}
```

Rules:

- One `Intl` instance cached per `(locale, options)` key — constructors are
  expensive (repeated formatting in templates/views).
- **Explicit `locale` + `timeZone` parameters, never ambient server
  defaults** — the SSR-hydration rule (AD-19 D5). The service defaults from
  its constructor options; callers pass the request locale explicitly.
- `Intl.PluralRules` is exposed via the i18next adapter (i18next uses it);
  no direct wrapper unless a consumer needs one.

### 2.4 Locale flow — `@blue/dispatcher` + platforms

**`@blue/dispatcher`** (`src/language-resolver.ts`):

- `FixedLanguageResolver extends AbstractLanguageResolver` — always returns
  the configured language.
- `AcceptHeaderLanguageResolver extends AbstractLanguageResolver` — reads
  `Accept-Language` from `route.attributes` (the node adapter already
  parses headers into the route) using `parseAcceptLanguage` semantics
  (inlined or via a tiny local parser to avoid a dispatcher→content
  dependency — dispatcher does not depend on `@blue/content` today).
- `NavigatorLanguageResolver` stays (client default).
- `AsLanguageResolverStrategy` stays; the default resolver becomes
  `FixedLanguageResolver` at the platform, overridable per platform.

**`@blue/platform-node`**:

- `NodeAutoConfiguration` registers `AcceptHeaderLanguageResolver` as the
  dispatcher's language resolver (reads the parsed `Accept-Language` from
  the request the way the adapter already exposes headers).
- The resolved language is written to `route.attributes` (e.g.
  `LANGUAGE_ATTRIBUTE`) during dispatch so handlers/views can consume it.

**`@blue/platform-web`**:

- `CookieLanguageResolver` (persisted user override) + localStorage
  variant, ordered above `NavigatorLanguageResolver` in the strategy chain.
- A `locale` signal (`@blue/signals`) holding the active language;
  `changeLocale()` updates the signal + cookie/localStorage and triggers
  re-render through the existing signals wiring in views.

### 2.5 Context integration — `@blue/context`

`GenericApplicationContext` already implements `ContentSource`. Add:

- `ApplicationContext extends MessageSource` (interface level), delegating
  `getMessage` to the registered message-source bean, falling back to raw
  `ContentSource.getContent` when none is registered.
- `setMessageSource`/`getMessageSource` on the configurable context
  interface (parallel to `setContentSource`).
- `ApplicationContextAwareProcessor` injects the context into
  `MessageSourceAware` beans (one extra `likeMessageSourceAware` branch,
  mirroring the `ContentSourceAware` branch).

### 2.6 Template / island integration

- `@blue/view-ejs`: template locals gain `t(key, params)` (bound to the
  context's `MessageSource`) and the four formatters, resolving the locale
  from the current request. This is the EJS-view equivalent of Spring's
  `#{}`/`t()` helpers.
- `@blue/view-webcomponent` / islands (AD-9): the island contract already
  carries model + schema; the resolved locale is added so islands hydrate
  with client-side formatting identical to the SSR output.

## 4. Testing strategy

- Contract tests run against a fake `MessageSource` (no i18next in the
  contract package).
- i18next adapter tests use in-memory `resources` (no network): plurals,
  contexts, interpolation, fallback chain, missing-key → key, per-call
  language, `changeLanguage`/`preload`.
- Formatter tests assert explicit locale/timeZone behavior and cached
  instances; SSR parity is asserted by formatting the same value twice —
  once as "server" (request locale + pinned timezone), once as "client"
  (same inputs) — and requiring identical strings.
- Integration: real HTTP request to `blue-island` with `Accept-Language`
  asserts a translated, correctly formatted page; the todo client test
  asserts a locale switch re-renders without reload.
- No per-format hot-path overhead: formatter instances are cached per
  `(locale, options)`.

## 5. Acceptance criteria

1. `MessageSource.getMessage(key, params?, language?)` composes
   `ContentSource` and falls back to the key; exposed on `ApplicationContext`
   and injected into `MessageSourceAware` beans.
2. `@blue/content-i18next` `I18nextMessageSource` supports interpolation,
   plurals, contexts, fallback chains, lazy preload, and per-call language —
   all behind the `MessageSource` contract; `@blue/content` has no i18next
   dependency.
3. `@blue/core` formatters use `Intl.*` exclusively, cache instances, and
   take explicit `locale`/`timeZone`; identical SSR and client output for a
   pinned timezone.
4. Node requests resolve language from `Accept-Language`; client locale
   persists (cookie/localStorage) with precedence user > navigator > fixed,
   and a `locale` signal re-renders on switch.
5. `blue-island` serves a localized page; `blue-todo` switches locale
   reactively. Both demo suites green.
6. Full workspace build/test/lint/format clean; docs + graft refreshed.

## 6. Non-goals

- No message-formatting engine, plural-rule tables, ICU parser, or CLDR
  data (AD-19 D6).
- No `@locale` handler-parameter decorator in this change (a later
  convenience; locale is on the route/request and context).
- No translation-management tooling or content-authoring UI.
- No change to existing `ContentSource`/`Theme`/`LanguageResolver`
  behavior — all additions are additive.

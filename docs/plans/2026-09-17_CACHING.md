# 2026-09-17 Caching Abstraction

> **Current-contract supersession (2026-10-01):** This historical plan preserves
> the original decisions below. The async Cache cutover required by
> [AD-40](../decisions/2026-10-01_AD40_PERSISTENCE_BASELINE.md), following
> [AD-39](../decisions/2026-09-30_AD39_ASYNC_BY_DEFAULT.md), supersedes its
> synchronous store and return-shape contracts: `get`/`set`/`has`/`delete`/
> `clear` and `size()` now return promises; `getCache`/`hasCache` remain
> synchronous local handle-registry operations. `@cached` requires
> Promise-returning methods; `memoize` always returns a promise, including
> for synchronous input. Single-flight spans read through computation and
> write, scoped to the actual store. Read errors reject; decorator write
> failures warn best-effort without losing the computed result. This cutover
> adds no distributed backend. See the [live guide](../guides/07-caching.md).

## 1. Problem

The gap analysis records the caching story as client-side-only:

> Only client-side HTTP caching (`cache-interceptor`, `if-modified-interceptor`).
> No server cache-aside, TTL store, or cache annotations.

Seq item #4 names the fix shape: **"`@cacheable` decorator + in-memory store
in the signals/ORM style."** This plan builds that, with three owner
constraints that change the shape:

1. **Client-side is in scope too.** The HTTP-client cache exists
   (`CacheInterceptor` — in-memory, TTL default 5 min, 100-entry cap, LRU-ish
   eviction via `lastAccessed`; `IfModifiedInterceptor` — ETag/Last-Modified
   conditional requests), but there is **no application-level memoization
   anywhere in the repo** (verified: no `memoize` in `ndigo-util` or any
   package). The same store abstraction should serve both sides.
2. **No AOP, no pointcuts, no proxies required.** The repo already has the
   interception idiom: a TC39 method decorator returning a wrapper function
   that reads a collaborator off the instance — `@transactional`
   (`ndigo-orm/src/decorators.ts:336-370`: wrapper resolves
   `this.transactionManager`, calls through when absent). Mirror exactly that.
3. **No `-able` decorator names.** Verified: **zero** decorators ending in
   `-able`/`-ible` exist in any package (`@[A-Za-z]+(able|ible)` over
   `packages/` → no matches). The audit's `@cacheable` is a Spring echo that
   would be the first. See D-1.

## 2. Current state (verified 2026-09-17)

- `CacheInterceptor` (`ndigo-http/src/interceptors/cache-interceptor.ts`):
  `Map<string, CacheEntry {response, expiry, lastAccessed}>`, bypass list,
  key `method:url`, TTL + max-size config. Self-contained; HTTP-specific
  semantics (response objects, cache-busting headers).
- `TtlContentSource` (`ndigo-content/src/async.ts:29-96`): the repo's TTL
  pattern — `Map<string, { value, expiresAt }>`, lazy expiry on read.
  No size cap, no eviction policy.
- `@transactional` (`ndigo-orm/src/decorators.ts:336-370`): wrapper pattern —
  `context.metadata[transactionalMetadataKey] = true`, returned function reads
  `this.transactionManager`, graceful call-through when absent. **This is the
  interception mechanism for `@cached`.**
- `@scheduled` (`ndigo-scheduler/src/scheduled.ts`): spec-normalization
  decorator (`resolveScheduledSpec`), `SCHEDULED_METADATA_PREFIX = 'schedule:'`,
  per-method metadata keys, `getScheduledSpec` reader. **This is the
  spec/metadata shape for `@cached`.**
- `NodeAutoConfiguration` (`ndigo-platform-node/src/node-auto-configuration.ts`):
  `@entry` beans (`taskScheduler()`, `scheduleRegistry()`) — **this is where
  the zero-wiring server bean lands.**
- No `memoize`/memoization utility anywhere (grep-verified).

## 3. Decisions

### D-1 — Name the decorator `@cached`, not `@cacheable`

`-able` decorators do not exist in this repo (evidence above); the repo's
decorator vocabulary is mixed but never `-able`: `@scheduled` (past
participle — closest functional analog: method execution transformed by the
framework), `@transactional` (`-al`), `@authenticated`/`@authorized`
(adjectives), `@service`/`@entry` (nouns), `@requestMapping`/`@socketMapping`
(`-ing`). `@cacheable` would add a new part of speech for no semantic gain and
echo Spring's annotation vocabulary rather than the repo's.

`@cached` parallels `@scheduled` exactly: verb root + `-ed`, describing the
method's execution semantics ("this method runs on a schedule" / "this
method's result is cached"). Pre-1.0 rename remains cheap if the vocabulary
audit below lands differently.

**Follow-up (out of scope, tracked):** decorator vocabulary is inconsistent
repo-wide (`-al`/`-ed`/adjective/noun mix). Schedule a separate
decorator-vocabulary ADR + audit when convenient; a lint rule
(`@ndigo/oxlint-plugin`) could enforce the chosen convention going forward.

### D-2 — One isomorphic package `@ndigo/cache`; client and server share the store

Both sides get the same abstraction; no platform code in the package:

- `Cache` — store contract (sync; async loading is the caller's/memoize's job).
- `MemoryCache` — TTL + max-size in-memory store (the `TtlContentSource`
  expiry pattern + `CacheInterceptor` eviction pattern).
- `CacheManager` — named-cache registry (`getCache('users')`, auto-create with
  defaults).
- `memoize(fn, options)` — keyed-by-args memoization for plain functions;
  **isomorphic** (browser + Node), async-aware (in-flight coalescing,
  rejections never cached).
- `cached(spec)` — method decorator (D-3).
- Node auto-configuration lives in `ndigo-platform-node` (bean), exactly like
  `taskScheduler` (AD-20): the package itself imports only `@ndigo/core`
  (error types) + `@tsmetadata/polyfill`.

Client story: `memoize` needs no DI, no bean — a browser app memoizes a fetch
or a pure computation with a one-liner and gets the same TTL/size behavior as
the server decorator. `@cached` works in the browser too when the instance
carries a `cacheManager` (explicit construction; no web auto-config in this
wave).

### D-3 — No AOP: wrapper decorator with graceful degradation

`@cached` mirrors `@transactional` verbatim in mechanism:

```ts
return function (target: Function, context: ClassMethodDecoratorContext): Function {
    if (context.kind !== 'method') throw new TypeError(...);
    context.metadata[`cache:${String(context.name)}`] = spec;
    return function (this: { cacheManager?: CacheManager } | undefined, ...args: unknown[]) {
        const manager = this?.cacheManager;
        if (!manager) return target.apply(this, args);      // degradation, like @transactional
        const cache = manager.getCache(spec.cacheName);
        const key = resolveCacheKey(spec.key, args);
        const hit = cache.get(key);
        if (hit !== undefined && !(hit instanceof CacheMiss)) { ... }  // see D-4 sentinel
        const result = target.apply(this, args);
        if (isPromise(result)) result.then(v => cache.set(key, v, spec.ttl), () => {});
        else cache.set(key, result, spec.ttl);
        return result;
    };
};
```

No pointcuts, no `Proxy` machinery, no bytecode. Self-invocation through
`this.method()` **is** cached (the wrapper replaces the prototype method —
stronger than Spring proxy semantics, where self-invocation bypasses; document
this).

### D-4 — Values are stored; `CacheMiss` sentinel; async via promise-aware set

- `MemoryCache` stores values with `undefined`-safe semantics: `CacheMiss`
  (symbol-branded class) distinguishes "no entry" from a stored `undefined`
  (industry pattern; Spring has the same problem with `null`).
- Caching **fulfilled** results only. Rejected promises / thrown errors are
  never stored; the failure propagates to the caller and the next call retries.
  This is a deliberate divergence from HTTP caching (which may cache error
  responses); document it.
- Coalescing (single-flight) is a `memoize` feature: concurrent calls for the
  same key share one in-flight promise. `@cached` does NOT coalesce in v1
  (decorator stays synchronous in shape; coalescing needs an async wrapper —
  adds nothing until a consumer needs it; noted as extension).

### D-5 — Keys are plain JS functions, not SpEL

`key` option: static string (method caches a single value) or
`(...args) => string`. Default: stable JSON of arguments (undefined-tolerant
serialization, arg order significant). No expression language — the repo's
stated JS-idiom position (assessment §3.3: "Use TC39 decorators, interceptor
chains"). Document: args-only keys mean a shared cache across instances
collides on equal args; per-cache-name isolation is the mitigation, or a key
fn incorporating instance identity.

### D-7 — Eviction: Map-order LRU default, `fifo` option; core's `_lru-cache` stays private

`packages/ndigo-core/src/_lru-cache.ts` (private, capacity-only, used by `URLGlobPathMatcher`, 256 cap) does **not** move into `@ndigo/cache`: core is the base layer every feature depends on; importing it from `@ndigo/cache` would invert the dependency direction. Its **technique** does: `MemoryCache` adopts the O(1) Map-order LRU (get-hit → delete+reinsert; full → evict first map key) over the `lastAccessed` min-scan. `MemoryCacheOptions` gains `eviction: 'lru' | 'fifo'` (default `lru`); `maxSize` omitted = TTL-only, no size eviction (the `TtlContentSource` model). LFU/random explicitly out. Core's private copy stays for `URLGlobPathMatcher`; `CacheInterceptor`'s ad-hoc Map cache untouched (D-6).

### D-8 — In-memory only; store interface is the extension seam

`MemoryCache`/`MemoryCacheManager` are v1. Distributed/Redis adapters are
explicitly out of scope (consistent with the audit's "in-memory store"); the
`Cache`/`CacheManager` interfaces are the plug points. `CacheInterceptor` is
**not** refactored onto `Cache` in this wave (HTTP cache semantics — response
cloning, cache-busting headers, method:url keys — don't fit the generic
store; unification is a post-1.0 option).

## 4. Architecture

| Piece                                               | Home                                          | Notes                                                                                                                                           |
| --------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `Cache`, `CacheMiss`, `MemoryCache`                 | `packages/ndigo-cache/src/cache.ts`           | TTL lazy-expiry on read; `maxSize` evicts least-recently-used (`lastAccessed`); `get/set/has/delete/clear/size`                                 |
| `CacheManager`, `MemoryCacheManager`                | `packages/ndigo-cache/src/cache-manager.ts`   | Named caches, auto-create with defaults; `getCache(name)`                                                                                       |
| `memoize`                                           | `packages/ndigo-cache/src/memoize.ts`         | Keyed by args; `{ ttl?, maxSize?, key? }`; in-flight coalescing; rejection passthrough                                                          |
| `cached` + `CachedSpec` types + `resolveCachedSpec` | `packages/ndigo-cache/src/cached.ts`          | Spec normalization/validation (mirrors `resolveScheduledSpec`); `CACHED_METADATA_PREFIX = 'cache:'`; `getCachedSpec(target, methodName)` reader |
| `@entry cacheManager()` bean                        | `ndigo-platform-node` `NodeAutoConfiguration` | Zero wiring for Node apps (AD-20 pattern); bean name `cacheManager`                                                                             |
| Demo gate (server)                                  | `apps/ndigo-api`                              | `@cached` service method + counter spec (second call = 0 invocations)                                                                           |
| Demo gate (client)                                  | `apps/ndigo-views` `/client`                  | `memoize` on a client computation adjacent to the existing cache-hit-refresh demo                                                               |

Package deps: `@ndigo/core` (errors) + `@tsmetadata/polyfill` only; no browser
globals (passes `@ndigo/no-browser-globals-in-isomorphic`). Scaffold via the
package generator.

### API sketch (`@ndigo/cache`)

```ts
const cache = new MemoryCache({ defaultTtl: 60_000, maxSize: 1_000 });
cache.set('k', { any: 'value' }); // or cache.set('k', v, 5_000) per-entry TTL
cache.get('k'); // CacheMiss when absent/expired
cacheManager.getCache('users'); // auto-creates with defaults

const loadUser = memoize(async (id: string) => fetchUser(id), { ttl: 30_000 });
await loadUser('a');
await loadUser('a'); // second call: coalesced/instant

class UserService {
    cacheManager: CacheManager; // injected; required for caching
    @cached({ cacheName: 'users', ttl: 30_000 })
    async byId(id: string): Promise<User> {
        /* … */
    }
    @cached({ key: () => 'stats' }) // single static value
    stats(): Stats {
        /* … */
    }
}
```

## 5. Risks

- **Stale data / invalidation.** v1 ships TTL + `cache.delete`/`clear` (manual
  invalidation via `CacheManager`); no `@cacheEvict`-style annotation (Spring
  parity would need a second decorator + wrapper composition — defer, note in
  ADR). Cache-aside docs must state the invalidation contract.
- **Args-only keys + shared manager** → cross-instance collisions (D-5
  documents the mitigation).
- **Async `@cached` returns the live promise**, not a settled one: two callers
  get the same promise object only with coalescing (v1: both call target; one
  result is stored). Correct, slightly redundant; documented.
- **`this`-dependent results**: caching a method whose output varies with
  instance state is the caller's contract (same caveat as `memoize` purity).
  Wrapper only keys on args.

## 7. Verification

- `Cache`/`MemoryCache`: TTL expiry (lazy, on read; per-entry overrides),
  `maxSize` eviction order (LRU via `lastAccessed`), `CacheMiss` vs stored
  `undefined`, `delete`/`clear`.
- `memoize`: stable keys (undefined handling), per-key TTL, coalescing
  (one in-flight call; concurrent callers share), rejected promise not cached
  (next call re-invokes), `maxSize` eviction.
- `cached`: hit path (second call → target not invoked), TTL honored, miss →
  set, rejection not stored, no-manager call-through (degradation), metadata
  written/readable via `getCachedSpec`, non-method → TypeError.
- Demo counter spec: `@cached` method invoked once across two dispatches.
- Repo gates: `pnpm lint` (`--deny-warnings`), `pnpm format:check`,
  package `tsc -b`, package `vitest run`.

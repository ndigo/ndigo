### 2.2 Security — config-server client (`@ndigo/context` remote-property-source) + secrets demo

**SEC-1 (Must Fix) — documented `https:` enforcement does not exist.**
`[code]` Module docs: "the URL scheme must be `https:` (enforced at load — config in transit is a secret-bearing channel)" (`remote-property-source.ts:32-33`, `:70-71`). Constructor only rejects an empty URL (`:136-148`); `#fetchAndApply` passes the option URL straight to `fetch` (`:226-227`); the app feeds `NDIGO_CONFIG_SERVER_URL` from env unvalidated (`apps/ndigo-api/src/index.ts:74-84`) and forwards `Authorization: Bearer <token>` to whatever host it names. An operator error or influenced env value silently downgrades a secret-bearing channel to plaintext HTTP.
**Mitigation:** when the default fetch is used, require `new URL(url).protocol === 'https:'` at construction/load (reject `http:`/`ftp:` with an error naming the variable), keeping the injected-fetch escape hatch; add a spec with an `http://` URL.

**SEC-2 (Must Fix) — poll-time failures are unhandled promise rejections (process crash).**
`[code]`+`[exec]` `start()` schedules `setInterval(() => void this.#poll(), pollMs)` (`:189`); `#poll` awaits `#fetchAndApply` with no try/catch (`:207-210`); throwers are transport failures from `await doFetch` (`:226-227`) and malformed JSON/body (`:250-262`). Comment "errors are handled inside" (`:209`) is false. Corroborated by three independent review passes; probe: a fetch rejection during a poll tick produced `process 'unhandledRejection' → 'fetch failed: ECONNREFUSED'` — fatal under Node ≥15 defaults. Only `!response.ok` failures take the keep-last-good branch (`:234-237`).
**Mitigation:** wrap the poll body in try/catch: log a warning, keep last-good, retry next tick (with optional backoff); add an in-flight guard (see ARC-4) and a spec firing a rejecting fetch mid-poll.

**SEC-3 (Must Fix) — `optional: true` (the default) is inert for transport failures at boot.**
`[code]`+`[exec]` `#handleBootFailure` is reachable only from the `!response.ok` branch (`:306-311`); a fetch rejection (DNS/TLS/refused) propagates through `load()` → `Application._prepareEnvironment` → boot aborts "Application startup failed" despite the documented "fetch failure at boot warns and proceeds" contract (`:31-33`, `:84-88`). Probe: `load()` rejected with `ECONNREFUSED` under `optional: true`. Three failure behaviors (HTTP-error → policy, transport/parse → always throw, post-success → silent) form no single convention.
**Mitigation:** route fetch-level and parse failures through the same optional/last-good policy as HTTP errors (`catch → lastBody === null ? handleBootFailure : null`), with the cause logged when optional.

**SEC-4 (Must Fix) — `GET /api/config/secrets` returns the decrypted secret to any caller.**
`[code]` `apps/ndigo-api/src/config-secrets-controller.ts:42-46` returns `{ secretToken: config?.secretToken ?? "unset" }` with no auth, no profile gate, no env check; registered unconditionally (`node-app-configuration.ts:143-145`). The controller's own docstring states it "reveals the plaintext". With `NDIGO_SECRET_KEY` set (`index.ts:67-69`) any process reaching the port (default `127.0.0.1` bind, but any proxy/host override) reads the plaintext secret via a cross-site-triggerable GET. Contrast with the app's own gating patterns: `note-controller.ts:11-17` (Bearer via `lookupPrincipal`) and `@profile("dev")` (`node-app-configuration.ts:173-176`).
**Mitigation:** gate like the other demo gates (Bearer validated against `auth-store.ts` and/or `@profile("dev")`), or return decryption _presence_ rather than the value, or drop it from production wiring.

**SEC-5 (Must Fix) — multipart bodies have no byte cap before or during consumption.**
`[code]` The multipart branch bypasses `#readBody` — the only hard cap (`maxBodyBytes` 1 MiB default, `http-request-limits.ts:44-47`) — entirely (`node-http-server-adapter.ts:831-833`); the parser's `totalBytes` counter only sets a sticky abort flag while busboy drains the whole request (`parse-multipart.ts:185-190`), and the 413 is produced only after EOF. With `Expect: 100-continue`, Node sends 100-continue as soon as reading starts, so an attacker streams an arbitrarily large body and the server ingests it all under the 30 s request timeout (bandwidth/time DoS; also inconsistent: a 1 MiB+ JSON body is cut off, a multipart body is fully downloaded). 10 MiB parser `maxRequestSize` vs 1 MiB body cap defaults disagree.
**Mitigation:** reject 413 up front when `Content-Length` exceeds the cap (without reading; no 100-continue then), cap the streaming read itself (`#readBody`-style limiter), and surface parser limits through `NodeHTTPServerAdapterOptions`.

**SEC-6 (Must Fix) — spilled multipart temp files are never deleted.**
`[code]` Parts above the 128 KiB `fileThreshold` stream to `os.tmpdir()` (`parse-multipart.ts:292-293`); `cleanup()` is called only on the parser-abort path (`:236`) — the adapter's `handleRequest` (`node-http-server-adapter.ts:934-951`) and the demo controller never call it; tests clean up manually (`multipart-http.spec.ts:131`, `parse-multipart.spec.ts:83`), confirming the framework does not. Doc contracts "cleaned up by the framework request lifecycle" (`parse-multipart.ts:241`, `upload-controller.ts:19-20`) are unfulfilled. Every upload >128 KiB leaks a named temp file containing uploaded bytes for process lifetime → unbounded disk growth (disk-fill DoS), shared-/tmp disclosure.
**Mitigation:** `try/finally { await nodeRequest.multipart?.cleanup() }` after dispatch in the adapter (idempotent; runs after handlers' `transferTo`), mirror in `MockHTTP.request` (`mock-http.ts:221-226`), fix the doc comments.

**SEC-7 (Should Fix) — rejected/aborted multipart parts stall the parser (socket pinning DoS).**
`[code]` Rejected parts (traversal filename → `sanitizeFilename` null) and post-abort parts are abandoned as `void stream.resume()` with no consumer (`parse-multipart.ts:160-174`); busboy's `FileStream` is push-based, so an unconsumed ~64 KiB buffer halts the parser until the 30 s request timeout kills the request — a cheap request-rate DoS loop.
**Mitigation:** drain rejected streams with a real consumer (`stream.on('data', noop).on('end', noop)`) before moving on, so busboy reaches `close`.

**SEC-8 (Should Fix) — static serving buffers whole files; Range/HEAD/304 read everything.**
`[code]` `_resolveFile` does `readFile(real)` of the ENTIRE file on every request (`static-resource-resolver.ts:229-247`) — including HEAD, conditional GETs (304 check happens after the read, `static-resource-handler.ts:199-206`) and Range requests (then `subarray()`s bytes out of the full buffer, `:213-215`). No servable-size cap. A large file in the static root (default `cwd/public`) becomes a memory-exhaustion primitive under concurrency.
**Mitigation:** serve via `createReadStream` + stat-derived `Content-Length`; Range via `{start,end}` stream; answer 304 from stat only; optional max-size rejection.

**SEC-9 (Should Fix) — multipart text fields are silently truncated at 1 MiB.**
`[code]` busboy's hard-coded default `fieldSizeLimit` truncates over-limit parts and flags `valueTruncated`; the parser neither passes a `fieldSize` limit nor checks the flag (`parse-multipart.ts:147-150,171-178`) — a >1 MiB `requestPart`/meta field binds as a silently truncated string.
**Mitigation:** expose `maxFieldSize` in `MultipartLimits`, pass to busboy, and treat `valueTruncated` as 413 `field_too_large`.

**SEC-10 (Should Fix) — secrets wiring is fail-open when the key is unset.**
`[code]` `builder.secrets(...)` is called only when `NDIGO_SECRET_KEY` is set (`apps/ndigo-api/src/index.ts:67-69`); otherwise markers bind as literal `{cipher:v1:...}` strings and `SecretsConfig.secretToken` defaults to `"unset"` (`server-config.ts:33-35`) — a misconfigured deployment silently uses ciphertext/placeholder as a live credential, contradicting the cipher's documented fail-loud posture (`aes-gcm-cipher.ts:13-15`).
**Mitigation:** when any source contains `{cipher:` markers but no decryptor is wired, warn at boot (or fail for `*secret*`/`token`/`password` keys); or always wire `AESGCMCipher.fromEnvironment()` so a missing key surfaces at first lookup.

**SEC-11 (Should Fix) — decrypt-then-convert error path can echo plaintext.**
`[code]` `getRequiredPropertyAs` converts the **post-decrypt** value (`property-resolver.ts:479`); the NaN diagnostic embeds the value with `JSON.stringify` (`:598-608`) — a `{cipher:...}` marker read as an untyped numeric property puts decrypted plaintext into `IllegalStateError` text that reaches boot logs and error responses. Everywhere else in the slice values are redacted.
**Mitigation:** redact the value in `#convert` diagnostics when a decryptor is configured.

**SEC-12 (Should Fix) — poll failures after first success are silent staleness.**
`[code]` Keep-last-good returns `null` with no warning, log, or event (`remote-property-source.ts:231-237`); no logger/telemetry exists in the file. A config server carrying rotated/revoked secrets loses all observability.
**Mitigation:** warn on keep-last-good; expose `lastError`/`lastOkAt` on the source for health endpoints.

**SEC-13 (Must Fix) — MockHTTP turns multipart 400/413 into 500 plain JSON.**
`[code]` The mock's catch unconditionally writes `500 {'Content-Type': 'application/json'} {error}` (`mock-http.ts:259-268`), while live the adapter maps `RequestLimitError` → problem documents at 400/413 (`node-http-server-adapter.ts:1017-1035`; parser throws at `parse-multipart.ts:135-136,159-160,181-182,227-231`). The added comment "Parse errors land in this catch and map to a problem response, as they do live" (`mock-http.ts:219-221`) is the opposite of the code; any limit/validation test through the harness asserts mock-only behavior.
**Mitigation:** mirror `#writeErrorResponse` — `err instanceof RequestLimitError` → `writeProblem(status=err.statusCode, urn:ndigo:<code>)`, fallback 500 also as problem+json.

### 2.3 Architecture — config refresh (AD-29)

**ARC-1 (Must Fix) — refresh is non-atomic and listener failures are swallowed.**
`[code]`+`[exec]` The emitter catches listener exceptions and re-dispatches them as an `'error'` event (`_event-emitter-helpers.ts:366-389,176-180`); nothing in boot subscribes to `'error'`, so it vanishes (probe: an explicit error listener was required to surface the failure). Failure sequence: remote document drops a required key → `#apply` commits the new source and calls `refresh()` → resolver rebuild committed → `refreshScope.clear()` runs; if a `@destroyable` callback throws, `scope.ts:289-295` aborts **before** `#instances.clear()`, so the pre-refresh instance stays cached and is served → the boot rebind listener (`application.ts:447-457`) throws on the second config class → first class rebound, second not, old instance still bound under the name, no rollback, no log — the app runs half-refreshed.
**Mitigation:** (1) register a fail-loud `'error'` handler on the environment (or wrap refresh dispatch in try/catch that logs and rethrows into the poll error path); (2) order rebind-then-clear or restore the previous document on failure; (3) make `RefreshScope.clear()` always reach `#instances.clear()` (callbacks best-effort).

**ARC-2 (Should Fix) — configServer precedence fallback inverts documented order.**
`[code]`+`[exec]` `#register` falls back to `addLast` when neither `systemEnvironment` nor `application` exists (`remote-property-source.ts:290-296`) — but in the real boot flow `defaults` is always registered first (`application.ts:511-512`), so the fallback places configServer BELOW `defaults`/`boot`, inverting D-7 (`commandLine > boot > systemEnvironment > configServer > dotenv > application > defaults`). Probe: `["defaults","configServer"]` order; `server.port` resolved 8080 from defaults while the remote document held 9090. Untested fallback path.
**Mitigation:** fall back to `addBefore("defaults", name, document)`; add a no-platform/no-loader precedence test.

**ARC-3 (Should Fix) — consumers keep stale references after refresh.**
`[code]` Refresh re-creates bound entries (`scope.ts:289-295`) and re-binds `@configurationProperties` names (`application.ts:447-457`), but never re-injects dependents: a controller that captured `serverConfig` at construction keeps the old value forever — silent divergence between `env.getProperty`, the bean, and the consumer's captured value. `refresh-scope.spec.ts` asserts only the bound entry's identity change.
**Mitigation:** document the snapshot semantics in the refresh guide now; design a dependency re-injection pass (or documented "inject the environment" consumer pattern) as follow-up.

**ARC-4 (Should Fix) — no in-flight guard on polling; out-of-order apply possible.**
`[code]` `setInterval` fires `void this.#poll()` regardless of the previous fetch (`remote-property-source.ts:189`); with `pollMs` under fetch latency, two fetches overlap and responses apply out of order — an older document can win after a newer one (regressing rotated/revoked secrets until the next poll).
**Mitigation:** in-flight flag (skip a tick whose fetch is unresolved) or sequence numbers on the applied document.

**ARC-5 (Optional) — two parallel listeners implement one `@refreshScope` annotation.**
`[code]` Context clears the lazy scope (`generic-application-context.ts:444-451`) while boot eagerly re-binds config classes (`application.ts:435-457`) — mixed graphs update at different moments; ordering is implicit.
**Mitigation:** single refresh coordinator next time the behavior grows; pin listener ordering in a spec.

**ARC-6 (Optional) — `config:refresh` subscriptions are never detached on close.**
`[code]` Neither the context's `#wireRefreshScope` nor `Application`'s rebind listener is removed on `close()` (`generic-application-context.ts:429-451`, `application.ts:457`) — a dead context stays reachable through the environment; a later refresh writes into a closed context silently.
**Mitigation:** store `(environment, listener)` pairs; `off()` in `close()`.

**ARC-7 (FYI) — placeholder cache vs in-place source mutation; index divergence.**
`[code]` `#placeholderCache` clears only on registry version/refresh (`property-resolver.ts:536-547,588-595`), while `PrototypeChainIndex` claims live visibility of in-place mutations and `FlatMergedIndex` snapshots (`:109-208`) — same edit, different staleness per index option. Boot path uses version-bumping `replace`, so not a live bug.
**Mitigation:** document the divergence in `ResolverOptions`; consider snapshotting for both indexes.

### 2.4 Design, naming, code reuse — argument binding (AD-27) and cross-cutting

**DSG-1 (Should Fix) — unserved whole-source types silently bind `undefined`.**
`[code]` `SOURCES_BY_KIND.route` admits all five `data-*` types (`parameters.ts:773-777`) with the comment "registration on the other transport is a no-op" (`:770-772`) — but no matching resolver ⇒ `RouteHandlerMethod.invoke` gets `null` and the handler receives `void 0` (`route-handler-method.ts:110-114`), silently, even for `required` extractors (the required check lives inside resolvers). `dataBinderValue('body')` on web or `dataBinderValue('session-storage')` on node compiles and binds undefined.
**Mitigation:** fail fast — throw naming the parameter/type when no resolver matches (mirroring the socket path's close-on-missing), or validate data-* sets against the assembled resolver chain.

**DSG-2 (Should Fix) — `parameters.ts` is a 977-line god-module.**
`[code]` Five concerns in one file (types, `MethodParameterType` enum + `data()` cache, `MethodParameter`, 18 factories + 7 wrappers, decorator/registration/validation); +154 lines this wave; it is the 63-edge hotspot of the repo.
**Mitigation:** split `parameter-types.ts` + `parameter-factories.ts`, keep decorator/validation in `parameters.ts`, re-export so the public surface is unchanged.

**DSG-3 (Should Fix) — browser storage resolvers are four copies of one loop.**
`[code]` `session-storage-argument-resolver.ts` and `local-storage-argument-resolver.ts` differ only in names (normalized diff: 0 code-line differences), and the same jar-dump loop is re-implemented inside `BrowserDataBindingMethodArgumentResolver.getSourceData` (`data-binding-argument-resolver.ts:58-72`) — four maintenance points for one behavior.
**Mitigation:** one parameterized `BrowserStorageValueMethodArgumentResolver(storage, type, tag)` (or a shared `dumpStorage` helper) registered twice; data-binder calls the same helper.

**DSG-4 (Should Fix) — node/web resolver plumbing is byte-identical twins.**
`[code]` `ndigo-platform-node/src/_resolver-util.ts` is a copy of the web package's (plus one helper); `argument-value-converter.ts` in both packages is code-identical (same registry, same converters). The dispatcher's own header advertises the consolidation goal ("Eliminates the 11 copies of the resolveArgument converter pipeline", `abstract-platform-resolver.ts:10-12`). Same-class twins got lockstep edits this wave (`'*'` → `''` in two files).
**Mitigation:** hoist `convertArgumentValue` + the converter registry into `ndigo-dispatcher` next to `AbstractPlatformArgumentResolver`; platforms re-export.

**DSG-5 (Optional) — header-argument-resolver hand-rolls what `@ndigo/http` cannot yet do.**
`[code]` `header-argument-resolver.ts:30-36` does `request.headers[name.toLowerCase()]` + array-join; `@ndigo/http`'s `HTTPHeader.get` is case-sensitive on plain records (`http-header.ts:59-71`) and has no array-join — so reuse is currently not possible without a helper upgrade. Latent gap, not a regression.
**Mitigation:** extend `@ndigo/http`'s record reads with case folding so `new HTTPHeader(name).get(request.headers)` works, then adopt; or document why not.

**RUS-1 (Optional) — content-type/boundary sniffing is hand-rolled in four places.**
`[code]` `extractBoundary` (`parse-multipart.ts:87-97`) is a case-sensitive regex on `boundary=` (R\FC 2045 §5.1 parameter names are case-insensitive — legal `BOUNDARY=x` is rejected) whose result is never used (busboy re-parses); the same `split(';')` sniff appears at `node-http-server-adapter.ts:828`, `http-request-limits.ts:103`, `mock-http.ts:222`. `MediaType.for` can't replace it (no quote stripping/case folding).
**Mitigation:** `/boundary=/i` + one shared `contentTypeBase` helper (candidate home: `@ndigo/http` once `MediaType.for` gains quoted-parameter parsing); or drop the pre-check and let busboy's own error code.

**RUS-2 (Optional) — static handler writes literal header-name strings.**
`[code]` `static-resource-handler.ts:144-160` etc. use `'Content-Type'`, `'Cache-Control'`, `'ETag'`, `'Last-Modified'`, `'Vary'` literals where `@ndigo/http` exports `HTTPHeader` constants (`http-headers.ts`) and `cors-interceptor.ts:123-166` establishes the constant-name precedent. Reads use lowercase literals (correct for Node records). Consistency only.
**Mitigation:** key the write side with `[CONTENT_TYPE.name]`-style constants; note the record-read convention in the module doc.

**RUS-3 (FYI) — `dotted-read` vs `parseKeypath` grammars diverge (`[code]` `dotted-read.ts:26-49` vs `keypath-expression.ts:20-84`); deliberate dot-only subset — document or unify behind a `readKeypath`.
**RUS-4 (Optional) — mock request headers are not case-normalized** (Node lower-cases `IncomingMessage`; `request-builder.ts:113-122` passes keys verbatim; a `Content-Type:` key silently skips the multipart parse gate `mock-http.ts:222`) — and non-multipart `rawBody` is silently dropped (`request-builder.ts:71-78`).
**RUS-5 (FYI) — static `acceptsHtml` does case-sensitive `includes('text/html')` and matches `q=0`** (`static-resource-handler.ts:242-247`); `remote-property-source.ts:174,180` handles the literal key `"If-None-Match"` case-sensitively against user headers. Both edge-only.

### 2.5 Tests, demo app, docs

**TST-2 (Should Fix) — keep-last-good rollback branch untested.** `[code]` All failure tests are boot-time (`remote-property-source.spec.ts:199,213`); no test proves a post-boot `!ok` poll preserves the last document, fires no event, and keeps ETag/body consistent.
**TST-3 (Should Fix) — static traversal tests are vacuous / absent.** `[code]` The "rejects percent-encoded traversal after decode" test asserts only "not ok" on an input nothing decodes (`static-resource-resolver.spec.ts:89-93`); no test sends traversal through handler/controller to the 403 branch; the resolver docstring "URL-decoded path" (`static-resource-resolver.ts:166`) describes a contract that doesn't exist (0 `decodeURIComponent` hits in platform-node/dispatcher/router) — encoded spaces/unicode filenames are permanently unservable. Defense layers are sound (see baseline) but unpinned.

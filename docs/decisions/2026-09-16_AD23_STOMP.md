# AD-23: STOMP Protocol Layer — codec, broker, client

**Date:** 2026-09-16
**Status:** Accepted — decision recorded; implementation sequenced (see
[plan](../plans/2026-09-16_STOMP.md))

## Background

The gap analysis records WebSockets as present-but-incomplete ("no STOMP");
AD-22 D5 reserved STOMP as the post-client future layer (destinations,
subscriptions, frames — codec in `@blue/socket`, server in
`blue-platform-node` or a sibling). BlueJS today has rooms + broadcast
(AD-21) and a reconnect client (AD-22), but no broker protocol over the
socket: no destinations, no subscription frames, no ack modes, no
receipts, no wire interop with STOMP clients (Spring `SimpMessagingTemplate`,
RabbitMQ/Artemis brokers, @stomp/stompjs).

The framing question: STOMP is a text protocol running _over_ the socket
contracts BlueJS already has — so do its parts land in the platform (which
owns the `ws` transport) or in the isomorphic socket domain package?

## Decision

### D1 — Protocol machinery is isomorphic and lives in `@blue/socket`

`StompBroker` (server) and `StompClient` (client) operate on `SocketSession`
/ `SocketClient` — contracts, not transports. Nothing in the protocol layer
touches `ws`, `node:http`, or the platform; it runs over any session
implementation (the Node adapter's `nodeSocketSession` today, a browser
session tomorrow). This is the same reasoning that placed the client in
`@blue/socket` (AD-22 D1): the WHATWG surface is isomorphic, so the
protocol is too. The platform's only new job is wire-level subprotocol
negotiation (D4). Package dependency stays `@blue/signals` —
`crypto.randomUUID` (WebCrypto, Node ≥19 and all browsers) generates
message/session ids; no `@blue/util` dependency needed.

### D2 — STOMP 1.2 core; answered-on-the-wire semantics

Implemented (2026-09-16, second wave — D7–D11 close the original
deferrals): CONNECT/CONNECTED negotiation (accept-version 1.0–1.2, reply
highest mutual), SEND, SUBSCRIBE/UNSUBSCRIBE, MESSAGE (per-subscription
framing + fresh `message-id`), ACK/NACK (parsed + validated; modes
accepted — see D9 for actual tracking/redelivery), receipts (RECEIPT for
every `receipt:` header), ERROR + close on protocol violations
(fail-closed, matching the repo posture), plus the second wave below.

### D7 — Transactions (BEGIN/COMMIT/ABORT) are brokered, not refused

PER-SESSION transaction buffers. BEGIN opens a named transaction (duplicate
id → ERROR + close); SEND/ACK/NACK frames carrying `transaction:` splice
their effect into the buffer; COMMIT applies the buffered operations in
order, ABORT discards them. Frames touching an unknown transaction id →
ERROR + close (fail-closed per D2). Receipts requested inside a
transaction are held and emitted on COMMIT/ABORT in order. No cross-frame
atomicity guarantees beyond ordering — that is the STOMP 1.2 bargain, and
exactly what Spring/Artemis clients expect.

### D8 — Binary frames and bodies are byte-exact

STOMP frames may carry binary (non-UTF-8) bodies via `content-length`. The
codec accepts `string | Uint8Array | ArrayBuffer | Buffer` inbound and emits
`string | Uint8Array` outbound (headers always text; body bytes verbatim).
The transport contracts gain this: `SocketSession.send` /
`SocketClient.send` treat `Uint8Array`/`ArrayBuffer` as binary frames
(strings stay text, other objects keep JSON parity), and server inbound
binary frames surface as `Uint8Array` (text frames stay strings) — a
pre-1.0 refinement of the "strings for both" promise, which could not
carry real binary. `content-length` is emitted for binary bodies on
serialization and honored byte-exact on parse.

### D9 — Ack tracking + NACK redelivery (bounded, in-memory)

Ack modes `client` and `client-individual` gain real semantics: the broker
tracks delivered-but-unacked messages per subscription (`maxUnacked`,
default 1000, FIFO eviction past the bound — the in-memory bound that
keeps NACK honest without a store). ACK in `client-individual` mode
removes exactly the named message; in `client` mode it acknowledges it and
all earlier unacked (STOMP 1.2 §1.4.1 cumulative semantics). NACK applies
the same removal rule **and redelivers** the message with `redelivered:
true` (1.2 §1.4.2). Acknowledging an id that already fell off the bound is
a tolerated no-op. Auto mode stays untracked.

### D10 — `/user` destinations: principal-scoped routing

`StompBroker` takes a `resolveUser(session)` seam (default reads
`session.attributes.user` — the adapter's `authenticate` hook populates
attributes, AD-21). SUBSCRIBE to `/user/<suffix>` registers a
principal-scoped subscription; `sendToUser(user, suffix, body, headers?)`
(SimpMessagingTemplate's `convertAndSendToUser` analog) fans out to the
scoped subscribers of that user, MESSAGE frames carrying the `/user/...`
destination (Spring convention). A session with no resolvable user
subscribing to `/user/*` → ERROR + close. A client SEND to `/user/<suffix>`
delivers only to the sender's own scoped subscriptions — cross-user
fan-out is the app's `sendToUser` call, never a client SEND.

### D11 — `/queue` destinations: bounded store-and-forward, not topics

SEND/publish to `/queue/<name>` appends to a per-destination backlog
(`queueBacklog`, default 1000 messages, FIFO eviction — bounded in-memory,
the honest pre-store contract answer). Live subscribers get the message as
usual; a **new** subscriber first receives the backlog replay (newest
last, their own subscription id, ack-tracked per the subscription's mode),
then live traffic. `/topic/*` and anything else stay pure fan-out. Queue
replay is delivery, not redelivery — no `redelivered: true` on backlog
messages. Still deferred: durable storage (M4 store contract, post-1.0).

Deferred as non-goals (unchanged): **STOMP over TCP — never** (the user's
call: WebSocket is the only transport with consumers — browsers, STOMP.js,
Spring); SockJS — never (AD-22 D4); durable persistence behind `/queue`
needs the audit's store contract (D11 keeps the seam bounded in memory).

### D3 — Heart-beat negotiated off; the WS layer owns liveness

CONNECTED answers `heart-beat: 0,0`. The AD-21 registry already pings every
session (`heartbeatIntervalMs`, default 30s) and reaps silent peers (`1001`)
— a second STOMP-level beat stream would duplicate the machinery and add a
parsing path for no observability gain. Inbound and outbound STOMP empty
frames are tolerated (a lone newline parses as a ping frame) for
interop with clients that do send them.

### D4 — `@stompMapping` + `handleProtocols` for the `v12.stomp` subprotocol

The `ws` server accepts a `handleProtocols(protocols, req)` hook at upgrade
time. A `@stompMapping` decorator (mirror of `@socketMapping` adding a
`route:stomp:<method>` marker) declares the endpoint speaks STOMP; the
adapters' hook then selects the client's offered `v12.stomp` (falling back
to v11/v10) only for those paths. Non-STOMP socket paths keep the current
behavior exactly — without a hook, `ws` echoes the first offered protocol;
the hook returns that same first value for non-stomp paths, so nothing
changes outside STOMP (verified against `websocket-server.js:400-417`, where
a falsy return merely omits the response header — it never aborts the
handshake).

### D5 — Destinations are broker state, not rooms; SEND fans out by default

A STOMP destination is a subscription namespace owned by the broker
instance (`Map<destination, Map<subId, { session, ack }>>`), not a
registry room: two subscriptions to one destination on the same session
must stay distinct, and MESSAGE frames must carry the _subscriber's own_
`subscription` id (a registry `broadcastTo` sends one payload to everyone —
the wrong shape for per-subscriber framing). Fan-out sends a MESSAGE frame
per subscription. SEND to a destination publishes to its subscribers,
including the sender when subscribed (room-echo parity); an optional
`onMessage` hook intercepts (return `false` to suppress the default). This
keeps the existing rooms/broadcast API untouched — rooms for raw fan-out,
broker destinations for STOMP, both usable side by side.

## Consequences

- **`@blue/socket`**: `stomp-frame.ts` (codec, pure), `stomp-broker.ts`
  (server state machine + fan-out table), `stomp-client.ts` (CONNECT,
  subscriptions, receipts, reconnect re-CONNECT/re-SUBSCRIBE), index
  exports; tests for each.
- **`blue-dispatcher`**: `@stompMapping` + `isStompMapping` (metadata
  marker only — dispatcher execution path unchanged).
- **`blue-platform-node`**: adapter `handleProtocols` (subprotocol
  selection per path); node socket session gains binary-frame delivery
  (`Uint8Array` inbound, binary send) — D8.
- **Demo gate**: blue-api `/stomp/chat` — `StompBroker` bean +
  `@stompMapping` handler + scheduler tick into a destination; e2e with
  two `StompClient`s.
- **Second wave (D7–D11)**: transactions with per-session buffers; ack
  tracking + NACK redelivery (`maxUnacked`, `redelivered: true`);
  byte-exact binary frames; `/user` scoped routing (`resolveUser` +
  `sendToUser`); `/queue` bounded store-and-forward (`queueBacklog`).
- **Deferred, documented**: durable persistence behind `/queue` (needs
  the audit's store contract — post-1.0), **STOMP-over-TCP — never** (no
  consumers: browsers, STOMP.js, and Spring all speak the WS variant),
  SockJS — never (AD-22 D4), cross-node pub/sub unchanged (post-1.0,
  needs a store contract).
- **Docs**: guide 06 STOMP section; plans index; gap analysis §2.3 row
  update (STOMP no longer a missing piece).

**Decision record:** this ADR. **Implementation plan:**

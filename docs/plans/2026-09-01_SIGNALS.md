# Signals — Modernizing `@blue/reactive`

**Date:** 2026-09-01  
**Package:** `@blue/reactive` → `@blue/signals`  
**Status:** Planning  
**Depends on:** Nothing (standalone)

---

## 1. Motivation

The current `@blue/reactive` package provides a **pull-based observable** pattern (Knockout/Backbone style):

```ts
const name = mutableModel('hello');
name.get(); // 'hello' — manual read
name.set('world'); // manual write
name.subscribe((v) => console.log(v)); // manual subscribe
```

This API has several problems:

- **No automatic dependency tracking.** `DerivedModel` requires explicit source arrays: `derived([a, b, c], (a, b, c) => ...)`. If you forget a source, it silently doesn't react.
- **Manual subscription management.** Every `.subscribe()` returns an `Unsubscribe` function. Forgetting to call it leaks memory. In practice, developers either leak or write tedious cleanup boilerplate.
- **No effect batching.** `batch()` exists but is opt-in. Without it, every `set()` fires subscribers immediately, causing cascading re-renders.
- **Verbose for simple cases.** Reading a signal requires `.get()` instead of `signal()`. Writing requires `.set(v)` instead of `signal(v)`.

**Signals solve all of these** with a **push-based** model where dependencies are tracked automatically at read time, and updates propagate through a microtask-scheduled effect queue.

## 2. Existing Library Landscape

| Library             | Stars      | Size       | Notes                                                                                                           |
| ------------------- | ---------- | ---------- | --------------------------------------------------------------------------------------------------------------- |
| **@preact/signals** | 3.5k+      | ~1.5 KB    | Most mature JS signals library. Preact team maintains it. Works with any framework. Uses a single global batch. |
| **SolidJS signals** | 35k+       | Bundled    | Built into SolidJS. `createSignal`, `createEffect`, `createMemo`. The reference implementation.                 |
| **Angular signals** | —          | Bundled    | Part of Angular 17+. `signal()`, `computed()`, `effect()`. Standardized.                                        |
| **Vue 3 `ref()`**   | —          | Bundled    | Vue's reactivity uses signals internally via `ref()` and `computed()`.                                          |
| **@vue/reactivity** | Standalone | ~5 KB      | Vue's reactivity extracted as a standalone package. Battle-tested.                                              |
| **svelte/store**    | —          | Standalone | Svelte's `writable()` and `derived()`. Pull-based stores, not true signals.                                     |
| **RxJS**            | 32k+       | ~30 KB     | Observable streams with operators. Heavy for signal use cases.                                                  |
| **valtio**          | 9k+        | ~3 KB      | Proxy-based state. Simple but different mental model.                                                           |
| **jotai**           | 22k+       | ~3 KB      | Atomic state. Atom → derived → subscribe. Signals-adjacent.                                                     |

### Recommendation: Build on `@preact/signals-core`

**Why Preact Signals:**

- **Dual-license (MIT).** Can vendor or depend freely.
- **Framework-agnostic.** Works in any JS/TS app, not tied to Preact/React.
- **Smallest and fastest.** ~1.5 KB gzipped, single global batch.
- **Strong semantics.** `.value` getter/setter, `computed()`, `effect()`, `batch()`.
- **No Proxy magic.** Clean transparent getter/setter — no `Proxy` overhead or compatibility issues.
- **Preact team backing.** Maintenance track record.

**Why not the others:**

| Library         | Issue                                                          |
| --------------- | -------------------------------------------------------------- |
| SolidJS         | Built into JSX compiler — extracting is fragile                |
| @vue/reactivity | Proxy-based — overhead per object access, edge cases with IE11 |
| Jotai / Valtio  | Different mental model — atoms vs. signals                     |
| RxJS            | 30 KB for what we need in 1.5 KB                               |

### Preact Signals Details

```ts
import { signal, computed, effect, batch } from '@preact/signals-core';

const count = signal(0);
const doubled = computed(() => count.value * 2);

effect(() => {
    console.log(`Count is ${count.value}`); // auto-tracked
});

count.value = 1; // triggers effect
```

**Primitives:**

- `signal<T>(value: T)` — writable signal with `.value` getter/setter
- `computed<T>(fn: () => T)` — derived, lazily evaluated, memoized
- `effect(fn: () => void)` — runs function, auto-tracks signal reads, reruns on change
- `batch(fn: () => void)` — batch updates, single notification
- `untracked(fn: () => T)` — read signals without tracking

## 3. Blue's Value-Add Layer

If we just re-export `@preact/signals-core`, we're a thin wrapper. The Blue twist is a **higher-level API** that integrates with Blue's framework patterns:

### 3.1 Decorator-Based API

The value-add is **declarative reactive state** using TC39 decorators:

```ts
import { signal, effect } from '@blue/signals';

class CounterStore {
    @signal count = 0;

    @computed get doubled() {
        return this.count * 2;
    }

    @effect track() {
        console.log(`Count changed to ${this.count}`);
    }

    increment() {
        this.count++;
    }
}
```

This is **not** just sugar — it solves real problems:

1. **`@signal`** — wraps a class field with `signal()`, exposes `.value` transparently. Reading `this.count` auto-tracks in a `@computed` or `@effect`.
2. **`@computed`** — wraps a getter with `computed()`, tracks dependencies automatically.
3. **`@effect`** — wraps a method with `effect()`, scopes lifecycle to the class instance (auto-cleanup on destroy).
4. **`@batch`** — batches all writes within a method into a single notification.

### 3.2 Resource-Scoped Lifecycle

Signals in current libs are global. Blue's context hierarchy gives us **scoped signal disposal**:

```ts
class AppComponent {
    @signal count = 0;

    @effect logCount() {
        console.log(this.count);
    }
    // When the component is destroyed (context closed):
    // 1. The effect is disposed
    // 2. The signal's subscribers are released
    // 3. Memory is reclaimed
}
```

This eliminates the dominant source of signal bugs: forgetting to `effect.cleanup()`.

### 3.3 Model Compatibility Adapter

The existing `ReadableModel`/`WritableModel` interfaces used across `@blue/view-wicket` need a **bridge**, not a rewrite:

```ts
import { signal } from '@blue/signals';
import { ReadableModel, WritableModel } from '@blue/signals/model';

// Signals ARE models:
const s = signal('hello');
const r: ReadableModel<string> = s; // ✅ compatible
const w: WritableModel<string> = s; // ✅ compatible

// Old code that takes ReadableModel still works.
// New code can use signal() syntax.
```

This lets us migrate `@blue/view-wicket` incrementally without a flag day.

## 4. Proposed API

### Core (re-exported from `@preact/signals-core`)

```ts
import { signal, computed, effect, batch, untracked } from '@blue/signals';

// signal
const s = signal(0);
s.value; // read
s.value = 1; // write

// computed
const c = computed(() => s.value * 2);

// effect
const dispose = effect(() => {
    console.log(s.value);
});
dispose(); // manual cleanup

// batch
batch(() => {
    s.value = 2;
    other.value = 3;
});

// untracked
effect(() => {
    console.log(
        s.value,
        untracked(() => other.value)
    );
});
```

### Blue Decorator API

```ts
import { signal, computed, effect, batch } from '@blue/signals';
import type { ReadableModel, WritableModel } from '@blue/signals';

@signal count: number = 0;
@computed get doubled(): number { return this.count * 2; }
@effect trackCount(): void { console.log(this.count); }
@batch updateBoth(): void { this.count++; this.other++; }
```

### Model Adapter

```ts
import { signal } from '@blue/signals';
import { toReadable, toWritable } from '@blue/signals/model';

// Wrap signal as ReadableModel/WritableModel
const s = signal(0);
const r: ReadableModel<number> = toReadable(s);
const w: WritableModel<number> = toWritable(s);

// The Wicket binding:
bindModel(component, 'value', toReadable(signal('hello')));
```

### Existing API Compatibility

The existing model types (`MutableModel`, `DerivedModel`, `StaticModel`, `CompoundModel`, `PropertyModel`) are deprecated but not removed. They'll be re-exported from `@blue/signals/legacy` during the migration window.

## 5. Migration Path

| Phase       | Changes                                                                                                       | Consumers Affected                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **Phase 1** | Create `@blue/signals` package. Depends on `@preact/signals-core`. Exports core + decorators + model adapter. | None — new package, no consumers yet                      |
| **Phase 2** | Add model adapter that lets signals implement `ReadableModel`/`WritableModel`.                                | `@blue/view-wicket` — signal can be passed to `bindModel` |
| **Phase 3** | Re-export legacy model classes from `@blue/signals/legacy`. Mark old `@blue/reactive` deprecation.            | `@blue/view-wicket` — switches import path                |
| **Phase 4** | Update `@blue/view-wicket` to prefer signal syntax where idiomatic.                                           | Internal consumers                                        |
| **Phase 5** | Remove `@blue/reactive` package (or freeze as compat shim).                                                   | End of migration                                          |

## 6. Packaging

```json
{
    "name": "@blue/signals",
    "description": "Blue Signals – Reactive state management with signals, computed values, and effects",
    "dependencies": {
        "@preact/signals-core": "^1.8.0"
    },
    "peerDependencies": {
        "@blue/core": "~0.0.1"
    },
    "sideEffects": false
}
```

**Why a new package instead of rename:** `@blue/reactive` is already consumed by `@blue/view-wicket` and the wicket-component generator. A rename would break every consumer simultaneously. A new package + deprecation path lets us migrate incrementally.

**Alternative considered:** Rename in-place. Rejected because it breaks `@blue/generators` template imports and requires a synchronized release of `@blue/view-wicket`.

## 7. Open Questions

| Question                                             | Options                                                               | Recommendation                                                                                                              |
| ---------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Vendor or depend on `@preact/signals-core`?          | (a) pnpm dependency, (b) vendor source                                | **Depend** — npm handles updates, smaller footprint, standard practice                                                      |
| Proxy-based `signal(obj)` for deep reactivity?       | (a) No — only top-level `.value`, (b) Yes — Vue-style deep proxy      | **No** — keep signals simple. Deep reactivity is a different concern (use `@blue/model` or zod schemas for data validation) |
| SSR compatibility?                                   | (a) Signals work on server (read-only), (b) Need special SSR handling | **Works on server** — signals are just values. `effect()` can be suppressed in server context                               |
| Class decorator vs. standalone functions?            | (a) Both, (b) Decorators only, (c) Functions only                     | **Both** — decorators for framework users, functions for library consumers                                                  |
| Should `@computed` return a signal or a plain value? | (a) Returns `ComputedRef<T>`, (b) Returns `T` directly                | **Return a signal** — allows passing computed value to other signal consumers                                               |
